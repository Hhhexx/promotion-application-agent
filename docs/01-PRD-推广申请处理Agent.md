## 1. 问题陈述

**谁**：MCN / 广告投放团队的投放运营岗与财务岗。
**什么场景**：每天在微信群里收到若干条"抖加申请总结""垫付申请总结"的自由文本，需要人工把里面的博主、金额、支付人、打款状态逐条抄进《推广账号表》，再汇总当天抖加与垫付总额，最后写一段汇报发给负责人。
**现在怎么解决**：纯人工。运营对着群消息和 Excel 表来回复制粘贴、肉眼核对。
**为什么不行**（来自行业调研，见第 3 节）：
1. **数据源割裂、对账靠手工**：申请记录、账号表、财务口径三处各自为政，人工抄录必然引入误差。行业基准显示，大量品牌方的达人付款记录在营销系统与财务系统之间**只有约 38% 能在无需人工订正的情况下对齐**（Influencers Time 行业基准调研）。
2. **重复付款与口径错位是真实财务风险**：同一达人既走了平台自动打款、又走了单独转账，就会产生重复付款；每一处人工步骤都是"500 元差异可以藏几个月"的漏洞。
3. **异常"不敢问也不会问"**：文本声称"共 7 笔"但明细只有 5 条、预计打款日期早于申请日期、同一博主出现两行——这些**信息量不足、无法安全自动判断**的情况，人工往往"顺手猜一个填进去"，把错误固化进账。
4. **汇报靠记忆**：负责人在群里要"今天花了多少"，运营需要临时翻聊天记录再手算。

**本产品的本质**：不是"自动填表机器人"，而是**"把重复的抄录与核对交给程序，把无法安全判断的部分原样交给人的异常闸门"**。核心价值是把"闷头猜着填"改成"暴露出来让人确认"。

## 2. 目标用户与诉求差异

| 角色 | 主要用户画像 | 核心诉求 | 对本产品的期待 | 最怕什么 |
|------|--------------|----------|----------------|----------|
| 投放运营（主要） | 25-35 岁，负责达人对接与申请登记，熟悉群聊与 Excel，技术水平偏低 | 少抄录、少返工、别背锅 | 一键导入文本→自动结构化→异常清单清楚→我点确认即可 | 程序把错的直接写进表，最后算我头上 |
| 财务 / 出纳（次要） | 30-45 岁，负责对账与打款，重合规与可审计 | 账实一致、有据可查、异常不放过 | 每条金额可追溯到原文与判定依据；异常必须有人签字 | 金额差异被静默吞掉、重复付款 |
| 负责人 / 团队主管（次要） | 30-45 岁，看结果不看过程 | 一眼看懂今天花了多少、有没有风险 | 简短汇报 + 异常红黄灯 + 谁在等确认 | 汇报里全是套话，看不到风险 |

**诉求冲突点（需设计上显式处理）**：运营要"快"，财务要"稳"，负责人要"准"。设计上通过**异常分级 + 人工确认闸门**同时满足：正常数据直通（快），异常一律拦截待确认（稳），汇报区分"已确认 / 待确认"两个口径（准）。

### 3.2 替代方案（现状土办法）

| 方案 | 做法 | 优势 | 劣势 |
|------|------|------|------|
| **Excel VBA 宏 + 手工 SOP** | 宏做条件格式标色、简单公式校验 | 零成本、就地可用 | 规则写死在宏里，改规则要改代码；无法理解自由文本；无审计留痕；复制宏即传播 |
| **纯人工 SOP（群消息 + 表格 + 复核）** | 人工抄录 + 第二人复核 | 灵活、能应付一切例外 | 慢、易错、不可追溯；人力随业务量线性增长（行业数据：中型机构每月仅达人付款对账就平均耗 8 小时） |

### 3.3 为什么选「单体 Agent + 规则引擎 + 人工确认闸门」而不是多 Agent

**产品侧论证素材（可直接用于面试陈述）：**

1. **任务本质是"确定性判定"，不是"开放式推理"**。本场景的判断（`金额是否对得上`、`是否重复`、`是否缺字段`）都是**规则可穷举的确定性判定**，专家包 `ai-agent-patterns.md` 的选型表明确：单一任务自动化 → **单 Agent + 工具链**，简单高效。多 Agent 的收益来自"多步骤、需专业化分工"（如 SEO 6 角色流水线），本场景并无此类分工。
2. **多 Agent 会引入"责任稀释"与"不可解释"**。当多个 Agent 互相传递结论时，出了错难以定位是谁的判定；而财务场景**最不能容忍的就是不可解释**（UiPath 之所以强调 audit trail，正是此因）。单体 + 规则引擎每一步判定都能落到一条可读的规则 ID 和原文证据。
3. **题目第 5 条是"禁止猜测"，这恰恰要求"低自主性"**。多 Agent / 强 LLM 自主性越高，越倾向于"顺着往下猜"。用**规则引擎做硬判定 + 人工确认闸门**，本质上是用工程结构强制"机器不越权"。
4. **LLM 的定位被刻意压低为"可选交叉校验"**。因为 LLM 对"950+300+300+200+500 是否等于 2250"这类算术与精确匹配不如规则引擎可靠，但它在"同一实体的模糊匹配"（如昵称写法差异）上可作**第二意见**。这符合行业共识：**真正的自动化不是零人工，而是把 5% 的例外路由给人，其余 95% 自动闭环**（Influencers Time）。
5. **成本与可维护性**：单体部署简单、调试直观、面试现场可讲解；多 Agent 的编排成本在此规模下是净负担。

| 对比维度 | 现成方案 | 本产品 |
|----------|----------|--------|

**一句话定位**：给每天都在"群消息 → Excel"之间人肉搬运的投放团队，一个**会喊"这里我不敢确定，请你确认"的对账助手**。

## 5. 功能清单与优先级（RICE 排序）

RICE：`Score = (Reach × Impact × Confidence) / Effort`
- Reach（1-10）：每季度受影响用户覆盖度
- Impact（0.25/0.5/1/2/3）：对单用户的影响
- Confidence（50%/80%/100%）：确信度
- Effort（1-10）：人月投入（1=半天，10=3 个月以上）

| 编号 | 功能 | 对应基础要求 | Reach | Impact | Conf | Effort | Score | 优先级 | MVP |
|------|------|--------------|-------|--------|------|--------|-------|--------|-----|
| F4 | 当天抖加 / 垫付金额汇总（多口径并列展示） | 要求 3 | 10 | 2 | 100% | 1 | **20.0** | P0 | 是 |
| F5 | 负责人简短汇报生成（含已确认/待确认双口径） | 要求 4 | 9 | 2 | 100% | 1 | **18.0** | P0 | 是 |
| F1 | 申请文本解析与结构化提取（账号/金额/支付人/打款状态） | 要求 1 | 10 | 3 | 100% | 2 | **15.0** | P0 | 是 |
| F2 | 异常检测引擎 + 人工确认闸门（核心评分项） | 要求 5 | 10 | 3 | 100% | 3 | **10.0** | P0 | 是 |
| F7 | 可运行 Web 演示（单页操作台） | 交付物 1 | 10 | 3 | 100% | 3 | **10.0** | P0 | 是 |
| F3 | 写入《推广账号表》测试副本（幂等、带溯源列） | 要求 2 | 8 | 2 | 100% | 2 | **8.0** | P0 | 是 |
| F8 | 全流程审计留痕 / 操作日志导出 | 交付物 2/3 | 5 | 3 | 80% | 2 | **6.0** | P1 | 否 |
| F6 | 人工确认工作台（异常队列、逐条确认/打回、备注留痕） | 要求 5 | 8 | 3 | 80% | 4 | **4.8** | P1 | 否（MVP 用轻量版：页面内确认区） |

>

## 6. 核心用户流程

```
[运营] 粘贴/上传申请文本（抖加 + 垫付）
   │
   ▼
[F1 解析] 结构化抽取：博主 / 金额 / 支付人 / 打款状态 / 日期 / 笔数声明
   │
   ▼
[F2 异常检测引擎] 逐条规则判定 → 生成异常清单（含规则ID/证据/级别/处置建议）
   │
   ├── 无 P0 异常 ──► 允许写入测试副本（F3），标记"低风险"
   │
   └── 存在 P0 异常 ──► 【硬暂停】不写入对应记录，进入待确认队列
                          │
                          ▼
                  [F6 人工确认] 运营/财务逐条选择：
                    · 确认按建议处置  · 修改后通过  · 打回重新提交
                          │
                          ▼
                  [F3] 确认后写入测试副本（附加 confirmed_by / confirmed_at / rule_id 溯源列）
   │
   ▼
[F4 金额汇总] 输出三口径并列：文本声明总额 / 明细求和 / 表内对应列求和
   │
   ▼
[F5 汇报生成] 简短汇报 = 今日抖加 + 今日垫付 + 已确认笔数 + 待确认异常摘要
   │
   ▼
[负责人] 查看汇报与红黄灯
```

**关键设计原则**：
- **P0 异常 = 硬暂停**：涉及金额、日期、重复的任何 P0 异常，**对应记录不落库**，避免"带病入库"。
- **默认不猜**：字段缺失时**留空 + 打异常标记**，绝不填默认值。
- **可回溯**：每一条写入的记录都能回答"它来自哪段原文、经过了哪条规则、被谁确认"。

## 7. 异常处理策略（评分核心）

### 7.1 总则

1. **三态处置**：`阻断（Block）` — 不写入、强制人工确认；`警告（Warn）` — 写入但打标、进入待确认可见列表；`提示（Info）` — 仅记录到日志与提示区，不阻断。
2. **禁止猜测原则**：凡触发异常，程序**不得**用默认值、上下文推断、或 LLM 猜测来"补全"缺失或冲突字段。
3. **证据可溯**：每条异常必须携带"引用原文片段 + 命中规则 ID + 参与计算的具体数值"。
4. **人工终裁**：任何 P0/P1 异常的最终处置由人决定，程序只做标记与建议。

### 7.2 异常规则清单（穷举）

> 下表为**逐条核对物料**后的穷举结果。判定式用类代码表达，字段名对应账号表 13 列。证据均来自 `题目物料.md` 原文。

#### P0 —— 阻断级（不写入对应记录，强制人工确认）

|--------|----------|--------------------------|------|----------|------------|------------------|

## 8. 验收标准（Given / When / Then）

- **AC-01（解析）** Given 一份抖加或垫付申请文本，When 用户点击"解析"，Then 系统输出结构化条目，每条含 博主昵称 / 金额 / 支付人 / 打款状态 / 日期，且金额保留原文数值不四舍五入。
- **AC-02（笔数校验）** Given 文本声明"共 7 笔"但明细仅 5 条，When 执行校验，Then 系统抛出 EXC-01（P0），且不将该批次写入测试副本。
- **AC-03（日期校验）** Given 申请日期 2026-09-03、预计打款日期 26/08/31，When 执行校验，Then 系统抛出 EXC-02（P0），并明确提示"8/31 早于 9/3，疑似倒挂或历史数据"。
- **AC-04（金额三口径）** Given 文本总额 700、明细求和 700、表内抖加列求和 400，When 执行汇总，Then 系统**并列展示三个数值**且标记"口径不一致"，不合并为单一数字。
- **AC-05（重复检测）** Given 表中"葵花夫妇"出现两行，When 执行匹配，Then 系统抛出 EXC-04（P0）并输出两行的关键差异（抖音号/报价/是否打款），要求人工选择。
- **AC-06（禁止猜测）** Given 某字段缺失，When 写入时，Then 系统**保持该字段为空**并打 P1 标记，**不得**填入默认值或从上下文推断。
- **AC-07（人工闸门）** Given 存在 P0 异常，When 用户未确认，Then 对应记录**不可写入**测试副本；用户确认后方可写入，并记录 confirmed_by / confirmed_at。
- **AC-08（幂等写入）** Given 同一批次重复点击"写入"，When 二次执行，Then 测试副本不产生重复行（以"批次号 + 博主"为幂等键）。
- **AC-09（溯源）** Given 任意一条写入记录，When 查看详情，Then 可追溯其"来源原文片段 + 命中规则ID + 确认人"。
- **AC-10（汇报双口径）** Given 存在待确认异常，When 生成汇报，Then 汇报必须区分"已确认金额 / 待确认金额"，并对异常给出红黄灯与"需谁确认"。

## 9. 边界条件与非功能需求

### 9.1 边界条件

| 类型 | 处理策略 |
|------|----------|
| 空状态 | 未导入文本时，操作台显示引导（"请粘贴当天的抖加/垫付申请总结"），不显示空白表格 |
| 文本为空 / 格式完全不符 | 返回"无法识别为申请文本"，不产生任何写入 |
| 明细为空但声明有总额 | 触发 EXC-03（P0），阻断 |
| 金额为 0 或负数 | 标记"金额异常"，进入待确认 |
| 加载状态 | 解析中显示进度与当前步骤（解析→校验→汇总） |
| 错误状态 | 规则引擎异常时降级为"仅解析不判定"，明确提示"校验未完成"，不静默通过 |
| 并发 | 同一批次并发提交以批次号为锁，先到先得，后到提示"该批次处理中" |
| 离线 | 纯本地运行，不依赖外网；LLM 交叉校验为可选开关，离线时自动跳过并提示 |
| 权限拒绝 | 非操作角色尝试写入时拒绝并记录（P2 阶段角色权限上线后生效） |
| 超长文本 / 多批次 | MVP 限单批次；超限提示分批粘贴（多批次进 Backlog） |

### 9.2 非功能需求

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 性能 | 单批次（≤50 条）解析 + 全量规则校验 < 2s；页面首屏 < 3s | P0 |
| 可用性 | 规则引擎为纯本地逻辑，无外部依赖即可完成核心流程；LLM 校验失败自动降级 | P0 |
| 安全 | 仅写"测试副本"文件，绝不触碰生产表；输入做长度与类型校验；不采集/不外传博主敏感信息 | P0 |
| 可解释性 | 每条异常附规则ID + 原文证据 + 数值明细 | P0 |
| 兼容性 | Chrome / Edge / Safari / Firefox 最新 2 版 | P1 |
| 数据埋点 | 核心动作埋点（见 9.3） | P1 |
| 可访问性 | 键盘可达 + 对比度达标（WCAG 2.1 AA 基本合规） | P2 |
| 图标方案 | 统一 SVG 图标库（具体由架构师按项目选型锁定，不预设具体库）；**不使用 emoji 作为功能图标** | P0 |
| 视觉基调 | 专业稳健、信息密度优先（对齐 `enterprise.md` 财务场景规范）；**不使用紫色→粉色渐变** | P0 |
| 国际化 | MVP 不涉及，预留文案抽取结构 | P2 |

### 9.3 数据埋点方案

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 获客/使用 | `page_view` | 操作台访问量 |
| 激活 | `source_text_submitted` | 用户提交申请文本（首个核心动作） |
| 激活 | `parse_completed` | 解析完成，含条目数 |
| 核心 | `anomaly_detected` | 触发异常，属性含 `rule_id` / `severity` / `count` |
| 核心 | `confirm_action` | 人工确认动作，属性含 `rule_id` / `decision`（通过/修改/打回） |
| 核心 | `record_written` | 写入测试副本，属性含 `batch_id` / `row_count` |
| 转化 | `report_generated` | 生成负责人汇报 |
| 留存 | `session_start` / `session_duration` | 使用频次与时长 |
| 异常 | `error_occurred` | 前端 + 后端错误 |

**埋点实现要求**：前端轻量 SDK（Mixpanel / Umami / 自建 `trackEvent()` 封装）；事件命名 `{对象}_{动作}`（如 `anomaly_detected`、`record_written`）；统一属性 `user_role` / `timestamp` / `device` / `version` / `batch_id`；**不采集博主隐私与原始输入全文**。

## 10. Out-of-Scope 清单（本次明确不做，每条带原因）

| 不做项 | 原因 |
|--------|------|
| 真实对接抖音 / 抖加后台 API 拉取数据 | 无授权且演示无必要，纯输入来自群文本，贸然对接反而引入不稳定依赖 |
| 真实写回生产《推广账号表》 | 题目明确要求"测试副本"，生产表写入有数据污染与合规风险 |
| 真实执行打款 / 支付动作 | 涉及资金安全，Agent 只给"建议与标记"，任何支付必须由人执行 |
| 用默认值 / 上下文推断 / LLM 猜测补全缺失字段 | 直接违反题目第 5 条"不要自行猜测" |
| 多 Agent 编排（如解析Agent+校验Agent+汇总Agent流水线） | 本场景为确定性判定，多 Agent 引入责任稀释与不可解释性，无收益（详见 3.3） |
| 多租户 / 完整 RBAC 权限体系 | MVP 为单操作台演示，权限为 P2 Backlog |
| 飞书 / 钉钉消息推送集成 | 演示阶段用页面内通知；真实 webhook 集成需企业配置，属增值非核心 |
| 历史数据全量迁移与全库对账 | 超出单批次核对范围，属数据治理项目 |
| 多级审批流引擎 | 本题只需"异常→人工确认"单级闸门，复杂审批属过度设计 |
| 移动端适配 / 原生 App | 使用场景为办公桌面端，投入产出比低 |
| 自动修复异常（自动合并重复、自动补齐缺失） | 属"猜测"的变体，违反核心原则 |

## 附录 A：物料事实核对备忘（供架构师做测试夹具）
