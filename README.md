# 推广申请处理台（推广申请处理 Agent）

> 把群里收到的自然语言《抖加申请总结》《垫付申请总结》转成**可核查、可追溯、可写入台账、可汇报**的结构化数据；对任何不确定项**零猜测**，一律标记并转人工确认。

这是一份**确定性的数据处理工作流**（不是多 Agent 自由对话），用于处理面试题「题目二：推广申请处理Agent」。

---

## 它解决什么问题

题目原文里的痛点是：

> 「根据题目提供的抖加申请和垫付申请信息，实现一个简单的 Agent 或自动化工作流……如果发现总额不一致、字段缺失、日期异常或重复申请，**不要自行猜测**，应标记并提醒人工确认。」

手工把群里的自由文本抄进 Excel 台账，会漏、会错、会重复，出错后也无法追溯；而「猜一个值填进去」比留空更危险——它把数据错误伪装成了数据完整。本项目的定位因此是**对账类（reconciliation）任务**，不是文本生成任务：第 5 条「不猜测」是**否决权规则**，优先级高于「把字段填满」。

## 30 秒跑起来

```bash
# 1. 安装依赖（建议在虚拟环境中）
python -m pip install -r requirements.txt

# 2. 启动服务
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

启动后打开：

| 地址 | 用途 |
|------|------|
| http://127.0.0.1:8000/ | 单页操作台（演示入口） |
| http://127.0.0.1:8000/docs | OpenAPI 接口文档（自动生成） |
| http://127.0.0.1:8000/health | 健康检查，返回 `{"status":"ok", ...}` |

前端是**无构建**的原生 HTML/CSS/JS，图标使用**本地化**的 Lucide（`web/vendor/lucide/lucide.min.js`），无需联网、无需 npm。服务启动时会自动登记仓库自带的测试用账号表（源表只读，服务端复制副本后再写）。

### 环境变量

| 变量 | 默认 | 作用 |
|------|------|------|
| `MST_DATA_DIR` | 仓库 `data/` | 重定向**运行期读写根目录**（`test-copies/`、`uploads/`、`decisions/` 都挂在它下面）。`tools/e2e_smoke.py` 与 pytest 会把它指向系统临时目录，从而**不写入仓库**。源表路径刻意**不受**该变量影响，始终指向仓库内只读源表。 |
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 未设置 | 可选 LLM 旁路；未设置 `LLM_API_KEY` 时自动降级为 no-op，主流程不受影响。 |

## 演示路径（照着点，含预期数字）

所有数字均为在本仓库实跑得到的结果，可用 `tools/e2e_smoke.py` 复现。

### 一、抖加批次：零阻断，直接入账

1. 打开 http://127.0.0.1:8000/ ，顶部应显示「测试副本 · 未污染原表」。
2. 在「申请文本」区选择 **抖加申请** 页签，点 **填充示例**（载入 `data/samples/抖加申请-2026-09-02.txt`）。
3. 点 **解析并校验**。
4. 预期结果：
   - 解析出 **4 条明细**：初秋 ¥300（分 3 笔）、艳红 ¥200（分 2 笔）、唐山第一女泵工 ¥100、戎大姨 ¥100；
   - 声明总额 **¥700**，明细求和 **¥700**（一致）；声明笔数 **7 笔**，分笔数求和 **7 笔**（一致）；合并 **4 笔** = 4 行（一致）；
   - **P0 阻断数 = 0**，批次状态 `READY`，可直接写入；共检出 13 条异常，全部为 P1/P2 提示。
   - 其中 1 条是 `CROSS_SOURCE_TOTAL_MISMATCH`：文本声明 ¥700，而账号表「抖加」列已有值合计 **¥400**。该条被**刻意降级为 P1 不阻断**（理由见下文「三口径并列」），只提示、不拦截。
5. 点 **写入测试副本**。预期：写入 **4 行**，`data/test-copies/` 下的副本被填充，源表字节不变。

### 二、垫付批次：3 个 P0，闸门拦截

6. 切到 **垫付申请** 页签，点 **填充示例**（载入 `data/samples/垫付申请-2026-09-03.txt`），点 **解析并校验**。
7. 预期结果：解析出 **5 条明细**、声明总额 **¥2250**（明细求和 ¥2250，金额自洽），但检出 **恰好 3 个 P0 阻断**：
   | 异常码 | 含义 | 证据 |
   |--------|------|------|
   | `MATCH_AMBIGUOUS` | 「葵花夫妇」在账号表命中 **2 行**（第 7 行报价 1000、第 9 行报价 100），无法自动判定写哪行 | 需人工指定目标行 |
   | `COUNT_MISMATCH` | 文本声明 **7 笔**，明细只有 **5 笔** | 声明值 7 vs 明细值 5 |
   | `DATE_ORDER_INVALID` | 预计打款日期 `26/08/31`（补全为 2026-08-31）**早于**申请日期 2026-09-03 | 文本值 `26/08/31` vs 申请日 `2026-09-03` |
8. 此时点 **写入测试副本**：预期被服务端拦截，返回 **HTTP 409**（`code=1003`），且副本**不发生任何写入**——这是「闸门不变量」，不靠前端禁用按钮。

### 三、人工裁决：逐层收敛，新问题浮出

9. 在「异常裁决工作台」逐条裁决。对 `MATCH_AMBIGUOUS` 必须走 **修正为某值** 并指定目标行（歧义不允许「确认无误」放行）。指定第 **7** 行后：
   - 该歧义异常被标记为**已裁决**；
   - 重跑校验**立即暴露一条新的 P0**：`CROSS_SOURCE_FIELD_CONFLICT` —— 打款人 文本「林老师」 vs 台账第 7 行「木木老师」。这正是「信息不丢失、逐层收敛」的演示：钉死目标行前，系统无法知道该行已填的打款人是否有冲突。
10. 继续裁决 `COUNT_MISMATCH`、`DATE_ORDER_INVALID` 与新增的 `CROSS_SOURCE_FIELD_CONFLICT`。全部 P0 裁决后，批次状态回到 `READY`。
11. 再次点 **写入测试副本**：预期返回 **200**，副本写入成功并带上 `_batch_id / _request_id / _confirmed_by / _confirmed_at / _dedup_key` 等**下划线溯源列**。
12. 重复点一次 **写入测试副本**：预期全部返回 `SKIPPED_ALREADY_WRITTEN`，副本行数**不变**（幂等）。

### 四、汇总、汇报与审计

13. 在「当日汇总」选择日期（默认 2026-09-03），查看**三口径并列**的金额数字（不合并）。
14. 点 **生成汇报**：产出面向负责人的简短卡片，区分「已确认金额 / 待确认金额」，列出待人工确认项数与「需谁确认」。
15. 点 **导出 CSV**：导出 append-only 的裁决日志，可回溯每条裁决的原始值与终值、操作人、理由。

## API 端点表

统一响应格式 `{ code, data, message }`，`code = 0` 表示成功；领域错误映射到 HTTP 状态码（参数校验 400、资源不存在 404、**闸门拦截 409**）。

| Method | Path | 作用 | 关键请求字段 |
|--------|------|------|--------------|
| POST | `/api/v1/account-tables` | 上传账号表并复制为测试副本；不传文件则登记仓库自带表 | `file`（multipart，可选） |
| GET | `/api/v1/account-tables/{table_id}` | 读取副本内容与元信息（列、行、空行引用） | 路径参数 `table_id` |
| POST | `/api/v1/requests/parse` | 解析申请文本 → `LineItem[]` + `ClaimSummary` + 分级异常 | `raw_text`、`biz_type_hint`、`table_id`、`enable_llm` |
| GET | `/api/v1/requests/{request_id}` | 获取解析结果、异常清单与闸门状态 | 路径参数 `request_id` |
| POST | `/api/v1/requests/{request_id}/resolutions` | 人工裁决一条异常并重跑校验 | `anomaly_id`、`decision`（accept/override/ignore）、`override_value`、`operator`、`note` |
| POST | `/api/v1/requests/{request_id}/commit` | 确认后写入测试副本（幂等）；有未裁决 P0 时 **409 且不写入** | `table_id`（可选） |
| GET | `/api/v1/requests/{request_id}/decisions` | 导出裁决日志（append-only） | `format`（`csv` 或 `json`） |
| GET | `/api/v1/summary` | 当日汇总，三口径并列 | `date`（必填）、`biz_type`（可选） |
| POST | `/api/v1/reports/daily` | 生成负责人汇报 | `date`、`include_unresolved`（可选） |
| GET | `/api/v1/reports/daily/{report_id}` | 获取汇报内容 | 路径参数 `report_id` |
| GET | `/health` | 健康检查（无鉴权） | — |

> `GET /api/v1/summary` 的 `date` 为必填查询参数，例如 `?date=2026-09-03`。

## 关键设计决策摘要

### 1. 确定性工作流，而非多 Agent

采用「普通工作流（确定性管线）+ 可选 LLM 单点旁路」。理由：本题输入是模板化文本、输出是固定结构表行、判定规则可枚举，属典型确定性数据处理；题目要求「不猜测」，而 Agent 的本质是自主决策，自主性越强越易猜；工作流把每步钉死，**天然满足不猜测**。单数据源单职责链无需并行探索，多 Agent 只增加协调成本。LLM 仅在配置了 `LLM_API_KEY` 时启用（仅用于实体模糊匹配），与规则冲突时**升级人工**而非择一，无密钥时自动降级为 no-op，主流程不受影响。

### 2. 源表只读 + 副本写入

源表 `data/你是我的仰望-推广账号表.xlsx` **只读**；服务端一律先复制到 `data/test-copies/tbl_copy_NN__*.xlsx` 再写。写入策略为**追加 + 下划线溯源列**（不覆盖既有值）。13 列按**回填权限表**逐列定义：

| 权限 | 字段 |
|------|------|
| 可回填（须过闸门） | 抖加、抖加支付人 |
| 人工确认后才可写 | 是否打款、打款人、打款日期 |
| 系统可写 | 备注（审计信息） |
| 禁止自动写 / 改 | 类型、抖音昵称、抖音号、报价、发布日期、是否接单、审核结果 |

其中「**报价**」列**永远只读**，任何写入路径直接抛错——「报价」是博主合作报价，「抖加」是流量券费用，二者语义与数值均不同，禁止互写。

### 3. 闸门不变量（不猜测的机制保证）

存在**未裁决 P0** 时，写表端点直接返回 **409 且不发生任何写入**（服务端强制，不靠前端禁用按钮）。状态机：`解析 → 校验 →（有未裁决 P0 → 409 / 人工裁决并写 append-only 日志 / 全部裁决 → 解锁写入）`。任何写入前必须经过 `READY`，任何 `READY` 必须无未裁决 P0。

### 4. 三口径并列，不合并

`GET /api/v1/summary` 返回**文本声明总额 / 明细行求和 / 表内该列求和**三个数值并列展示，**故意不合并成一个数字**——因为账号表「抖加」列没有批次/日期维度，无法证明表内值与当日声明额属于同一批次。对无法验证的等式施加阻断，会让每一批正常申请永远无法落表（表内累计额必然大于单日声明额），阻断会常态化、阈值退化为噪声。因此 `CROSS_SOURCE_TOTAL_MISMATCH` 定为 **P1 警告、不阻断**。

### 5. 幂等双键

| 键层 | 定义 | 用途 |
|------|------|------|
| 记录级 `dedup_key` | `biz_type\|日期(ISO)\|昵称归一\|金额(Decimal 2 位)\|支付人归一` | 判重，防重复写入同一笔 |
| 批次级 `batch_id` | `biz_type\|日期(ISO)` | 同批次重复提交识别 |

同一 `dedup_key` 再次提交返回 `SKIPPED_ALREADY_WRITTEN`（幂等，不重复写、不报错）。副本内还内嵌以 `_` 前缀的溯源列：`_batch_id / _request_id / _rule_id / _confirmed_by / _confirmed_at / _dedup_key`。金额全程使用 `Decimal` 保 2 位，禁止 float 参与运算。

### 6. 异常分级（25 个异常码 / P0·P1·P2 三档）

每条异常携带完整证据：`exc_id`（对应 PRD 编号）、`rule_id`、`code`、`severity`、`message`、`action_required`、`source_span`（原文定位区间）、`text_value` / `sheet_value`（冲突两侧取值）。**P0 仅限三类**：正确性缺陷 / 需求未满足 / 契约安全与数据完整性破坏。

```bash
# 端到端冒烟（不占端口，用 TestClient 走完整链路，共 114 条断言）

# 单元测试与接口回归（按归一化 / 解析 / 匹配 / 交叉校验 / 回填权限 / 闸门 / 端到端 / LLM 降级 / 不猜测分组）
python -m pytest -q
# 预期：165 passed

# 设计红线门禁（禁 emoji 图标 / 禁紫粉渐变 / 禁模板味文案）
python tools/check_p0.py docs web
# 预期：输出「P0 门禁通过」，退出码 0

# 代码行数门禁（单文件 ≤ 300 代码行，口径：非空且非纯注释行，docstring 计入）

# 预期：超限 0 个，退出码 0
```

`tools/e2e_smoke.py` 覆盖：健康检查 → 登记账号表 → 抖加批次（期望 0 个 P0）→ 垫付批次（期望 3 个 P0）→ 写表应被 409 拦截 → 逐条裁决 → 写表成功 → 幂等重放全 SKIPPED → 当日汇总 → 负责人汇报 → 裁决日志导出 → **源表零污染的字节级校验**（比对写入前后源表 sha256）。

## 已知边界 / 未做（锁定范围）

| 不做的功能 | 原因 |
|------------|------|
| 真实群消息接入（企业微信 / 飞书机器人） | 与题目「根据题目提供的申请信息」不符，需外部权限，投入产出比低 |
| 真实打款 / 财务系统对接 | 无接口，涉及资金安全 |
| 自动补齐缺失字段（按报价推断金额、填默认值） | 直接违反题目第 5 条，属「猜」 |
| 自动调和跨源金额差异（把 700 与 400 合并或取一） | 同上；口径未确认时任何合并都是编造 |
| 写入生产表 / 修改原表 | 原表是唯一事实来源，改动不可逆（只写副本） |
| 自动新建账号表行（匹配不到时） | 会凭空造出实体，属「猜」（须人工建行） |
| 多 Agent 协作架构 | 本题规模下协调成本大于收益 |
| 多歌曲 / 多项目台账 | 物料只涉及一首歌，引入泛化会稀释核心亮点 |
| 用户体系与权限控制 | 演示态单台，与核心机制无关 |
