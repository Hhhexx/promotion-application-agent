## 一、项目目标再判读

### 1.1 一句话定义

把"群里收到的 ChatGPT 风格自然语言推广申请摘要"，转成**可核查、可追溯、可写入台账、可汇报**的结构化数据；对任何不确定项**零猜测，一律标记并转人工确认**。

### 1.2 本质判定：这是"对账类"任务，不是"文本生成"任务

题面写着"实现一个简单的 Agent 或自动化工作流"，但 5 条要求里真正决定成败的是第 5 条。第 1~4 条（抽取 → 落表 → 汇总 → 汇报）是**数据管道**，第 5 条是**风控闸门**。

由此推导出三条贯穿全项目的判断：

| 判断 | 含义 | 对实现的约束 |
|------|------|--------------|
| 核心价值在校验，不在解析 | 解析错了页面还能跑；校验漏了就是假交付 | 异常规则必须先于代码冻结 |
| "不猜测"是一条**否决权**规则 | 不确定时的正确行为是"停下并标记"，不是"取最可能值" | 架构上必须存在阻断态与人工裁决入口，禁止任何自动兜底 |
| 可解释性权重高于功能数量 | 面试要讲解核心代码/工作流 | 每条判定必须能回答"凭什么这么判"，规则要可读、可追溯 |

### 1.3 成功判据

1. 演示能完整跑通"文本进 → 结构化出 → 异常被拦住 → 人工确认后落副本表 → 汇总与汇报出"。
2. 物料中真实存在的异常**全部被检出**，且每条都能指出证据位置。
3. 全程不发生任何未经人工确认的写表动作；重复运行不产生重复数据。
4. 面试时能讲清：为什么是这个编排形态、异常闸门怎么设计、AI 用在哪一步、哪些是 AI 产出哪些是人工修正。

## 二、范围边界

### 2.1 范围内（In-Scope）

| 编号 | 功能 | 验收标准摘要 | 优先级 |
|------|------|--------------|--------|
| F-1 | 申请文本结构化抽取 | 从抖加/垫付两类摘要中提取：博主昵称、抖音号、金额、笔数、支付人/打款人、打款状态、日期 | P0 |
| F-2 | 明细行与汇总声明分离建模 | 文本中"明细行"与"今日共 N 笔 / 已支付 ¥X"分别建模，用于交叉校验 | P0 |
| F-3 | 交叉校验与异常分级 | 输出 P0 阻断 / P1 警告 / P2 提示三级异常清单，每条附证据 | P0 |
| F-4 | 人工确认闸门 | 异常条目必须由人工裁决（确认无误 / 修正 / 打回），未裁决不得落表 | P0 |
| F-5 | 写入《推广账号表》测试副本 | 复制原表为副本，保留原表格式回填；原表零改动 | P0 |
| F-6 | 幂等与去重 | 同一申请重复处理不产生重复写入 | P0 |
| F-7 | 当日金额汇总 | 分别汇总当日抖加金额与垫付金额，并给出与声明值的比对 | P0 |
| F-8 | 负责人汇报生成 | 一屏可读的简短汇报：结论 + 关键数字 + 需决策项 | P0 |
| F-9 | 无 LLM 依赖可跑通 | 无任何 API 密钥时，全流程功能不降级 | P0 |
| F-10 | LLM 可选交叉校验 | 接入 LLM 后，与规则结果不一致处**升级为人工确认**，而非二选一 | P1 |

### 2.2 明确不做（Out-of-Scope，锁定）

| 不做的功能 | 原因 | 何时考虑 |
|------------|------|----------|
| 真实群消息接入（企业微信/飞书机器人） | 与题目"根据提供的申请信息"不符，且需要外部权限，投入产出比低 | v2.0，有真实使用场景时 |
| 真实打款/财务系统对接 | 无接口、涉及资金安全，非本次交付目标 | 生产化阶段 |
| 多歌曲/多项目台账管理 | 物料只涉及《你是我的仰望》，引入泛化会稀释核心亮点 | v2.0 |
| 用户体系与权限控制 | 面试作品无需，且与"异常闸门"这一核心无关 | 生产化阶段 |
| 历史台账全量治理与数据修复 | 属数据治理项目，会淹没主线 | 独立项目 |
| 自动修正或覆盖原表 | 原表是唯一事实来源，改动不可逆，风险不可接受 | 永不（只写副本） |
| 自动补齐缺失字段（如按报价推断金额） | **直接违反第 5 条**，属于"猜" | 永不 |
| 多 Agent 协作架构 | 本题规模下收益为负（见 §5） | 出现多源异构、多角色分工需求时 |

## 三、约束条件

| 类别 | 约束 | 影响 |
|------|------|------|
| 交付形态 | 可运行的 Web 单页操作台 + 代码仓库/压缩包 + 简短说明 | 演示需自解释，异常必须"看得见" |
| 解析策略 | 规则为主 + LLM 可选交叉校验 | 规则层是主干，LLM 是可插拔增强，不得成为硬依赖 |
| 技术栈 | Python + FastAPI + 轻前端 | openpyxl 保格式回填 xlsx |
| 输入特性 | ChatGPT 风格摘要，半结构化但**格式不稳定** | 解析器需容错 + 无法解析时明确报错，不得静默跳过 |
| 数据安全 | 只能写《推广账号表》**测试副本** | 仓储层需强制副本策略，原表路径只读 |
| 题目硬约束 | 第 5 条：不猜测，标记 + 提醒人工确认 | 架构必须存在阻断态与人工裁决节点 |
| 交付说明 | 需说明实现思路、遇到的问题、用了哪些 AI 工具、AI 生成了什么及做了哪些检查修改 | 开发过程需留痕（检查点、修正记录），不能事后补写 |
| P0 设计红线 | 禁 emoji 作功能图标 / 禁紫→粉渐变 / 禁 AI 模板味代码与文案 | 每个 Phase 门禁扫描 |

## 四、数据异常实测（项目总监亲自核对物料）

> 这一节是第一手事实核对，不是推测。后续 PM 的异常规则清单以此为基础穷举并补充。

### 4.1 自洽性核对结果

| 核对项 | 文本声明 | 明细实际 | 结论 |
|--------|----------|----------|------|
| 抖加金额 | ¥700 | 300+200+100+100 = **700** | 一致 |
| 抖加笔数 | "共 7 笔支付申请" | 3+2+1+1 = **7** | 一致 |
| 抖加合并数 | "合并同博主后为 4 笔" | 明细 4 行 | 一致 |
| 垫付金额 | ¥2250 | 950+300+300+200+500 = **2250** | 一致 |
| 垫付笔数 | "共 7 笔垫付申请" | 明细 **5 条** | **不一致，差 2 笔** |

**结论：抖加文本自洽；垫付文本笔数与明细不符，是本次交付必须命中的第一条异常。**

### 4.2 已实测异常清单（11 类）

| ID | 异常名称 | 触发条件（判定式） | 级别 | 物料证据 |
|----|----------|--------------------|------|----------|
| A-01 | 笔数声明与明细不符 | `声明笔数 != count(明细行)`（含"分 N 笔"折算） | P0 阻断 | 垫付：声明 7 笔，明细 5 条 |
| A-02 | 金额合计不符 | `sum(明细金额) != 声明总额` | P0 阻断 | 本次未触发（两边都自洽），但规则必须内置 |
| A-03 | 日期倒挂/时序异常 | `预计打款日期 < 申请日期` 或 `打款日期 < 发布日期` | P1 警告 | 垫付申请日 2026-09-03，"预计打款日期 26/08/31"（早 3 天） |
| A-04 | 日期格式不统一/年份歧义 | 同字段出现 >= 2 种写法，或出现 `4.9` 这类无年份写法 | P2 提示 | 表中 `4.9` / `4.10` / `2026/8/21` / `26/08/31` 混用 |
| A-05 | 重复申请/多行无法唯一匹配 | 解析出的博主命中 > 1 行且无法用抖音号消歧 | P0 阻断 | "葵花夫妇"出现 2 行（一行抖音号 LBXXnvzhuang，一行抖音号为空）；本次垫付含"葵花夫妇 ¥500" |
| A-06 | 关键字段缺失 | 必填字段为空却已产生业务动作 | P1 警告 | ① 马马马叔"是否打款=是"但打款人空；② 葵花夫妇(LBXXnvzhuang)"是否打款=是"但打款日期空；③ 沙雕动画整行空；④ @@陈三 / 一份大喜条 多字段全空 |
| A-07 | 跨文档口径冲突（支付人/打款人） | 文本声明的支付人/打款人 与 表中同批次记录不一致 | P0 阻断 | ① 抖加文本称"爆火音乐"，表中"高高"抖加支付人为"李老师"；② 垫付文本称打款人"林老师"，表中已打款记录打款人均为"木木老师" |
| A-08 | 与表内已有记录重叠 | 表中"抖加"列非空且博主/支付人与本次申请重叠 | P1 警告 | 表中已有抖加：高高 100（李老师）、张栋梁 200（爆火音乐）、葵花夫妇 100（爆火音乐）合计 400；本次抖加申请 700（4 位博主"抖加"列均为空）——是否叠加需澄清 |
| A-09 | 金额与报价关系异常 | `抖加金额 > 报价` 或金额口径与报价口径被混用 | P2 提示 | 表中葵花夫妇报价 100 / 抖加 100（等于报价）；初秋报价 400，本次抖加 300 + 垫付 950——抖加（流量券费用）与报价（合作费）是独立口径，禁止合并计算 |
| A-10 | 状态自相矛盾 | `是否接单=否` 却存在金额/打款记录；或审核结果为空却有打款 | P2 提示 | 君君动画（虾仁）、沙雕小子"是否接单=否"；"马马马叔"审核结果=过但打款人空 |
| A-11 | 幂等冲突 | 同一规范化复合键重复写入 | P0 阻断 | 规则型异常，非物料现存；复现方式为重复运行 |

### 4.3 由异常清单反推出的三条设计铁律

1. **A-01 / A-02 决定了解析层必须双模型**：只抽明细不行，必须同时抽"汇总声明"，否则无参照物做交叉校验。
2. **A-05 / A-07 决定了必须有阻断态**：这两类异常无法通过"更聪明的算法"解决，只有人工澄清一条路。系统必须能停在半途。
3. **A-06 / A-08 决定了回填必须分白名单/灰名单/黑名单**：程序可写哪些列、哪些列写了要标记、哪些列永不自动写，必须逐列定义。

## 五、关键决策预判：编排形态

题目要求"简单说明选择原因"，这是必答项。预判结论（由架构师在 ADR 中正式定稿）：

**选择「普通工作流 + 规则引擎 + 人工确认闸门」的单体形态，不用多 Agent。**

| 理由 | 说明 |
|------|------|
| 任务是确定性流水线 | 抽取 → 校验 → 裁决 → 落表 → 汇总 → 汇报，阶段固定、无分支探索，不需要 Agent 自主规划 |
| 可解释性优先 | 面试要讲清每一步凭什么这么判；多 Agent 的自由文本交接会稀释可追溯性 |
| 协调成本 > 收益 | 本题数据源单一（两段文本 + 一张表）、领域单一，拆多 Agent 只会增加通信开销与不确定性 |
| 确定性要求高 | 对账类任务不容许随机性；LLM 仅作为可选交叉校验器，且不一致时升级人工，不影响主干确定性 |

产品侧取舍：**"单 Agent"或"工作流"二选一即可说清，不必为了显得复杂而上多 Agent。**

## 七、第一步优先任务（本次核心结论）

### 7.1 结论

> **第一步：冻结「数据契约 + 异常规则清单 + 人工确认闸门」三件套，并汇编为 Spec v1.0。**
> 即：先定"什么是对的、什么是错的、错了怎么办"，再写一行代码。

### 7.2 为什么是这一步（理由）

1. **它是唯一无法靠写代码补齐的东西。** 代码写错可以重构，字段口径定错则解析、回填、汇总、汇报四处同时出错。四个下游模块共享同一份契约，契约先行可避免四处返工。
2. **它直接对应评分核心。** 第 5 条"不猜测、标记人工确认"的可执行形态，就是一张异常规则表加一道闸门。没有这张表，第 5 条就只是一句口号。
3. **物料的真实异常必须在动工前登记完毕。** 上一节已实测出 11 类异常（含垫付笔数差 2 笔、日期倒挂、葵花夫妇重复行、支付人三方冲突）。如果先写代码，极易做成"能跑通但漏检"的假交付——这是本题最大的陷阱。
4. **它是演示叙事的骨架。** 面试要讲"一段核心代码或工作流"，而核心正是"规则判定 + 阻断 + 人工裁决"这条链路。骨架先立，后面填的全是肉。
5. **它是前置依赖，不是可选项。** 解析器要按字段字典写、校验器要按规则表写、仓储层要按白/灰/黑名单写、测试要按金标准用例写。跳过它，后续每一步都在猜。
