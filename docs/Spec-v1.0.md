## 1. 产品定义

- **一句话描述**：把群里收到的自然语言《抖加申请总结》《垫付申请总结》转成可核查、可追溯、可写入台账、可汇报的结构化数据；**对任何不确定项零猜测，一律标记并转人工确认**。
- **目标用户**：三类角色，诉求不同——
  | 角色 | 诉求 | 在系统中的落点 |
  |------|------|----------------|
  | 投放运营 | 快速把群里文本变成台账，别让自己手工抄错 | 输入区 + 解析 + 异常裁决工作台 |
  | 财务/打款人 | 金额与支付人不能错，错了要能追 | 汇总三口径并列 + 溯源列 + 裁决日志 |
  | 负责人 | 一屏看完今天花了多少、哪里有风险、要我定什么 | 汇报卡片（结论 + 数字 + 需决策项） |
- **核心问题**：手工从自由文本抄进 Excel 台账，会漏、会错、会重复，且出错后无法追溯；而"猜一个值填进去"比留空更危险——它把数据错误伪装成了数据完整。
- **本质定位**：这是**对账类（reconciliation）任务**，不是文本生成任务。第 5 条"不猜测"是**否决权规则**，优先级高于"把字段填满"。

## 3. 明确不做（Out-of-Scope — 锁定）

> 每条带原因。开发中若有人提出这些功能，直接拒绝；确需变更则走 §13 变更流程。

| 不做的功能 | 原因 | 何时考虑 |
|------------|------|----------|
| 真实群消息接入（企业微信 / 飞书机器人） | 与题目"根据题目提供的申请信息"不符，需外部权限，投入产出比低 | v2.0 |
| 真实打款 / 财务系统对接 | 无接口，涉及资金安全 | 生产化阶段 |
| 自动补齐缺失字段（按报价推断金额、填默认值） | **直接违反题目第 5 条**，属"猜" | 永不 |
| 自动调和跨源金额差异（把 700 与 400 合并或取一） | 同上；口径未确认时任何合并都是编造 | 永不 |
| 写入生产表 / 修改原表 | 原表是唯一事实来源，改动不可逆 | 永不（只写副本） |
| 自动新建账号表行（匹配不到时） | 会凭空造出实体，属"猜" | 永不（须人工建行） |
| 多 Agent 协作架构 | 本题规模下协调成本大于收益（见 ADR-002） | 出现多源异构、多角色分工时 |
| 多歌曲 / 多项目台账 | 物料只涉及一首歌，引入泛化会稀释核心亮点 | v2.0 |
| 用户体系与权限控制 | 演示态单台，与核心机制无关 | 生产化阶段 |
| 历史台账全量治理与数据修复 | 属数据治理项目，会淹没主线 | 独立项目 |
| 移动端适配 | 对账场景是桌面长时间操作 | v2.0 |
| 引入数据库（SQLite/Postgres） | 演示态内存 + JSONL 足够（ADR-003） | 需要跨重启保留主数据时 |

### 4.2 架构分层（依赖方向只向下）

> 下表目录名为**实现落地后的真实名称**（初稿曾写作 `services/`、`renderers/`，已按实际代码校正）。

```
入口层  app/api/v1/          FastAPI routes —— 只做参数绑定与响应封装，零业务逻辑
   ↓
编排层  app/orchestrator/    pipeline（parse→validate→commit→summary→report）+ review_gate（人工闸门）
   ↓
解析层  app/parsers/         文本 → LineItem / ClaimSummary（保留 source_span 偏移）
校验层  app/validators/      规则引擎 → Anomaly（25 个异常码 + matcher + cross_check）
仓储层  app/repositories/    xlsx 只读源表 / 副本读写 / 回填权限表 / 裁决日志 JSONL 追加
输出层  app/reporters/       汇总三口径 / 汇报卡片
契约层  app/domain/          models（跨层数据契约）+ enums（异常码定档）+ errors
可选层  app/llm/             LLM 旁路（无密钥自动 no-op）
```

**硬规则**：单文件 ≤ 300 行；入口文件只装配零业务；逻辑下沉 service；routes/controllers 不得直接访问文件系统或 openpyxl。

### 4.3 编排形态（面试答辩口径，ADR-002 已定稿）

> **本题是强规则、强约束、要求"不猜测"的数据处理任务，故选确定性工作流而非 Agent**——每步可复现、可解释、可测试，天然满足"不猜测"；LLM 仅作可选语义交叉校验旁路，与规则不一致时升级人工而非择一。

不用多 Agent 的四条理由：① 确定性流水线，无开放推理需求；② 财务场景最忌责任稀释与不可解释；③ 第 5 条"禁止猜测"要求低自主性；④ 单数据源单领域，多 Agent 是净负担。

> 术语统一：PRD §3.3 的"单体 Agent"在本 Spec 中统一为**"单体确定性工作流"**，避免答辩口径不一。

### 4.4 异常分级与定档原则（P0 阈值边界）

**P0 仅限三类**：正确性缺陷 / 需求未满足 / 契约安全与数据完整性破坏。**不标**风格偏好、未被要求的额外特性、为覆盖率而覆盖率。

| 级别 | 语义 | 是否阻断写表 |
|------|------|--------------|
| P0 阻断 | 正确性缺陷，无法通过更聪明的算法解决，只能人工澄清 | **是**（服务端 409） |
| P1 警告 | 口径未知 / 范围差异 / 状态提示 | 否，写入后标注"待确认" |
| P2 提示 | 观察性提示 | 否 |

**关键裁决（已固化于 ADR-001，可直接答辩）**：跨源总额比较 `CROSS_SOURCE_TOTAL_MISMATCH` 定为 **P1 不阻断**。理由：账号表「抖加」列**没有批次或日期维度**，无法证明表内 400 与文本 700 属于同一批次；对一个**无法验证的等式**施加阻断，会让每一批正常申请永远无法落表（表内累计额必然大于任何单日声明额），阻断常态化即阈值失效。

### 4.5 人工确认闸门状态机

```
解析 → 校验 ─┬─ 无 P0 ──────────────→ 可写入（未裁决 P1 标注"待确认"）
             └─ 有未裁决 P0 ──→ 写入端点返回 409，不发生任何写入
                                  │
                     人工裁决（确认无误 / 修正为某值 / 打回重提）
                                  │
                             写 append-only 裁决日志
                                  │
                        全部 P0 已裁决 → 解锁写入
```

| # | Method | Path | operationId | 功能 | 认证 | 关键响应 |
|---|--------|------|-------------|------|------|----------|
| 1 | POST | `/api/v1/account-tables` | `uploadAccountTable` | 上传账号表，服务端复制为测试副本（源表只读） | 无（演示态） | `table_id` |
| 2 | GET | `/api/v1/account-tables/{table_id}` | `getAccountTable` | 读取副本内容与元信息 | 无 | 行数据 + 溯源列 |
| 3 | POST | `/api/v1/requests/parse` | `parseRequest` | 解析申请文本 → LineItem[] + ClaimSummary[] | 无 | 解析结果 + 异常清单 |

| 8 | POST | `/api/v1/reports/daily` | `createDailyReport` | 生成负责人汇报 | 无 | `report_id` + 卡片内容 |

**`commitRequest` 的三条服务端硬约束**（写入端点自带，不靠前端）：
1. 仅当请求**无未裁决 P0** 时允许执行；否则返回 **409 且不发生任何写入**；
2. 以 `dedup_key` 判重，已写入条目返回 `SKIPPED_ALREADY_WRITTEN`；
3. 「报价」列只读，任何写入路径直接抛错；「是否打款 / 打款人 / 打款日期」必须已存在人工裁决记录。

## 6. 数据模型与存储（锁定）

> 本题**不引入数据库**（ADR-003）。主数据在内存，产物落文件。

### 6.1 核心模型

| 模型 | 用途 | 关键字段 |
|------|------|----------|
| `LineItem`（行级申请条目） | 文本中的一条明细 | `line_no, biz_type, blogger_name_raw/norm, song_name, amount(Decimal), split_count, payer, request_date, source_span, dedup_key, match_result, state` |
| `ClaimSummary`（表级汇总声明） | 文本中的"今日共 N 笔 / 已支付 ¥X" | `biz_type, declared_total, declared_count, merged_count, payer, request_date` |
| `ViolationRecord`（异常证据对象） | 校验层 → 界面层的**唯一接口** | `rule_id, exc_id, code, severity, account_ref, field, text_value, sheet_value, source_span, impact_amount, action_required` |
| `ResolutionRecord`（裁决记录） | append-only 裁决日志的一行 | `anomaly_id, action(accept/override/reject), original_value, final_value, operator, decided_at, reason` |

**`ViolationRecord` 是强契约**：缺任一字段时界面降级显示"证据不完整"。这要求**解析器必须保留原文偏移映射**（`source_span`），不能只留解析后的值——否则界面无法高亮冲突 token。

### 6.2 幂等与去重（双键设计，锁定）

| 键层 | 定义 | 用途 |
|------|------|------|
| **记录级 `dedup_key`** | `biz_type \| 日期(ISO) \| 昵称归一 \| 金额(Decimal 2 位) \| 支付人归一` | 判重，防重复写入同一笔 |
| **批次级幂等键** | `biz_type \| 日期(ISO)` | 同批次重复提交识别 |

归一化步骤：去首尾空白 → 全角转半角 → 大小写归一 → 日期格式归一 → 金额统一 `Decimal` 保 2 位（**禁止 float**）。
> 注：PRD AC-08 表述的"批次号 + 博主"是本设计的粗粒度简化，实现以本节双键为准。

## 8. 设计 Token（锁定）

- **主题**：演示默认**浅色**。理由：对账核心是长文本阅读，浅底深字效率更高；投影环境对比稳定；"浅色 + 深靛蓝 + 1px hairline"读作账本/凭证，比深色 AI 面板更贴题。深色 Token 已备好可切换。
- **主色**：深靛蓝 `#3550B4` **纯色**（刻意避开反射式的 `#6366F1` 与紫→粉渐变）。每屏强调色 ≤ 2 处。
- **语义色三级**（本产品最重要的一组 Token，各绑定前景/背景/边框 + 图标 + 左边缘 3px 状态竖条 + 文字标签，**多通道编码不靠颜色单通道**）：
  | 语义 | 颜色 | 用途 |
  |------|------|------|
  | 正常/成功 | 绿 `#0F7A4F` | 校验通过 |
  | 警告 | 琥珀 `#9A5B06` | P1，可写但标注 |
  | 阻断/危险 | 朱红 `#B22A2A` | P0，禁止写入 |
  | 信息 | 蓝 `#1F5FA8` | 提示 |
  | 待确认 | 中性灰 `#647084` | 未裁决态 |
- **字体**：UI/正文 `Inter` + `Noto Sans SC`（中文兜底）；**金额/抖音号/日期/表格数字用 `JetBrains Mono` + `tabular-nums` 右对齐**（降低 0/O、1/l 误读）。字重 400/500/600，字号 8 级 12–40px。
- **图标库**：**Lucide**（唯一，禁止混用）。尺寸 16（行内）/ 20（按钮内）/ 24（独立）；颜色继承 `currentColor`。
- **Token 命名**：语义命名（`--color-*` / `--space-*` / `--font-*` / `--radius-*` / `--shadow-*`），禁止 `blue-500` 式原始命名；**禁止硬编码颜色值**（唯一例外 `#fff` / `#000`）。
- **动效**：禁止弹跳/弹性缓动 `cubic-bezier(0.68,-0.55,0.265,1.55)`；支持 `prefers-reduced-motion`。
- **产出物**：设计师 `03-UIUX设计方向.md` §3.7 已含 `design-tokens.json` 骨架；Phase 2 须落成 `design-tokens.css` + `DESIGN.md`。
- **对标品牌**：主对标 Stripe Dashboard，副语言 Linear，裁决结构参照人工复核队列（HITL）三栏工作台。

## 9. 验收标准（锁定 — EARS 格式，QA 测试的唯一依据）

| 编号 | 功能 | EARS 格式验收标准 | 优先级 |
|------|------|-------------------|--------|
| AC-01 | 解析 | 当用户提交一份抖加或垫付申请文本，系统**必须**输出结构化条目，每条含博主昵称/金额/支付人/打款状态/日期，且金额保留原文数值不四舍五入 | P0 |
| AC-02 | 笔数校验 | 如果文本声明"共 7 笔"而明细仅 5 条，系统**必须**抛出 `COUNT_MISMATCH`（EXC-01，P0）并禁止该批次写入测试副本 | P0 |
| AC-03 | 日期校验 | 如果预计打款日期早于申请日期，系统**必须**抛出 `DATE_ORDER_INVALID`（EXC-02，P0）并明确提示"早于申请日，疑似倒挂或历史数据" | P0 |
| AC-04 | 金额三口径 | 当执行汇总，系统**必须**并列展示"文本总额 / 明细求和 / 表内该列求和"三个数值并标记口径不一致，**不得**合并为单一数字 | P0 |
| AC-05 | 重复检测 | 如果解析出的博主在账号表命中 ≥ 2 行且无法用抖音号消歧，系统**必须**抛出 `MATCH_AMBIGUOUS`（EXC-04，P0）并输出各行关键差异，要求人工选择 | P0 |
| AC-06 | 禁止猜测 | 如果某字段缺失，系统**必须**保持该字段为空并打 P1 标记，**不得**填入默认值或从上下文推断 | P0 |
| AC-07 | 人工闸门 | 当存在未裁决 P0 异常，系统**必须**拒绝写入测试副本（HTTP 409）且不发生任何写入；人工裁决后方可写入并记录 `confirmed_by / confirmed_at` | P0 |
| AC-08 | 幂等写入 | 当同一申请被重复提交，系统**必须**不产生重复行（依据 §6.2 双键设计） | P0 |
| AC-09 | 溯源 | 当查看任一写入记录，系统**必须**可追溯其来源原文片段 + 命中规则 ID + 确认人 | P0 |
| AC-10 | 汇报双口径 | 当存在待确认异常，系统**必须**在汇报中区分"已确认金额 / 待确认金额"，并对异常给出红黄灯与"需谁确认" | P0 |
| AC-11 | 无密钥降级 | 在无任何 LLM 密钥的环境下，全流程核心断言**必须**仍全部通过 | P0 |
| AC-12 | LLM 冲突升级 | 当 LLM 交叉校验与规则结果不一致，系统**必须**将该项升级为人工确认项（`LLM_RULE_CONFLICT`），**不得**自行择一采信 | P1 |

## 10. 边界与约束

- **浏览器**：不支持 IE；仅 Chrome / Edge / Safari / Firefox 近两个大版本。
- **响应式**：桌面优先（对账为长时间桌面操作）；窄屏降级为纵向堆叠，裁决三栏折叠为 Tab。
- **性能目标**：单份申请文本解析 + 校验 < 1s（本地）；账号表（≤ 200 行）读取 < 2s。
- **无障碍**：`focus-visible` 可见、键盘可完成全流程、支持 `prefers-reduced-motion`；对比度与读屏专项检查留到 audit 阶段。
- **数据安全**：源表**只读**；一切写入仅作用于测试副本；不将敏感信息写入 Spec 或代码。
- **输入约束**：文本格式不稳定，解析失败**不得静默跳过**，须产出 `UNPARSED_LINE`（P0）+ 留存样本用于回归。
- **日期约束**：`4.9` / `26/08/31` 等缺年份或两位年份写法，允许按批次日期锚定推断，但推断值**必须**带 `inferred: true` 并置为待确认；无法唯一确定时抛 `DATE_UNRESOLVABLE`（P0）。
- **金额约束**：统一 `Decimal` 保 2 位，**禁止 float**。
- **LLM 边界**：默认关闭；开启后**仅允许用于实体模糊匹配**，**不得**参与金额、笔数、日期、支付人的判定。
- **P0 设计红线**：禁 emoji 作功能图标；禁紫→粉渐变；禁 AI 模板味代码与文案；禁硬编码颜色值。门禁工具：`tools/check_p0.py`。

## 11. 内嵌已知坑（从项目记忆拉取）

> 来源：`.workbuddy/memory/pitfalls.jsonl`。均为本次 Phase 1 真实踩到并有机械证据的坑。

| 坑 | 技术栈指纹 | 根因 | 修法 |
|----|------------|------|------|
| P0 门禁把勾叉记号（U+2713 / U+2717）判为 emoji | `tools/check_p0.py` | P0-1 正则以 Unicode 区块定义范围（含 U+2700–U+27BF Dingbats），而勾记 U+2713 / 叉记 U+2717 正好落在该区块内；区块范围宽于"emoji 功能图标"的语义意图 | 文档中改用文字表述（"一致" / "不一致"）；不使用勾叉类记号或形状类字符；确需保留时加 `p0-ignore` 行内标记 |
| 门禁把"禁令陈述"误报为违规 | `tools/check_p0.py` | 扫描器不区分上下文，形如"无 Lorem ipsum"的正向声明被当作字面命中 | 已实现命中点前 60 字窗口的否定词豁免；窗口不可取 14（实测 `无 "Welcome to" / "Lorem ipsum"` 间距 17 字，14 会漏） |
| 扫描器把自身正则当作违规 | `tools/check_p0.py` | 扫描器常量里必然写有违禁色值字面量，自扫必然报错 | 已排除自身路径；自测须用独立 fixture 目录（`.p0selftest`），测完清理 |
| 跨源总额比较被定为 P0 阻断，导致阻断常态化 | 校验层设计 | 账号表「抖加」列无批次/日期维度，"文本当日总额 == 表内累计求和"是**无法验证的等式**；表内累计必然大于单日声明额 | 降为 P1 不阻断，保留"禁止自动调和"；真正的 P0 只留给"同一博主同一字段值冲突" |
| 忽略 `source_span` 偏移导致界面无法高亮冲突 token | 解析层 | 解析若只留归一化后的值，界面拿不到原文位置 | `LineItem` / `ViolationRecord` 必须携带原文偏移；解析时同步保留原文映射 |
| 金额用 float 求和导致比对失败 | 解析层 / 校验层 | 二进制浮点无法精确表示小数，`0.1+0.2≠0.3` 类错误让金额校验随机失败 | 统一 `Decimal` 保 2 位；对金额求和与日期比较写**变异定向**用例（归一化写错必须变红） |
