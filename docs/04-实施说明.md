## 一、实现思路

### 1.1 一句话

把群里的自然语言《抖加申请总结》《垫付申请总结》转成可核查、可追溯、可写入台账、可汇报的结构化数据；**对任何不确定项零猜测，一律标记并转人工确认**。

### 1.2 数据流

```
输入文本
  │
  ▼
① 解析（双模型）      parsers/      文本 → LineItem[]（行级明细）+ ClaimSummary（表级汇总声明）
  │                                两个模型分开建模，才能交叉校验；保留 source_span 原文偏移
  ▼
② 校验（分级异常）    validators/   规则引擎 + 实体匹配 + 跨源交叉校验 → Anomaly[]
  │                                每条带 exc_id / rule_id / code / severity / 证据；25 码分 P0/P1/P2
  ▼
③ 人工闸门            orchestrator/review_gate    存在未裁决 P0 → 写表端点 409，不发生写入
  │                                人工裁决（确认无误 / 修正为某值 / 打回重提）→ append-only 日志 → 重跑校验
  ▼
④ 幂等写表            repositories/  过闸门后写入《推广账号表》**测试副本**，dedup_key 判重，追加 + 溯源列
  │
  ▼
⑤ 三口径汇总          reporters/     文本声明总额 / 明细求和 / 表内该列求和，**并列不合并**
  │
  ▼
⑥ 汇报卡              reporters/     负责人卡片：已确认金额 / 待确认金额 + 待人工确认项
```

各步输入输出均为 `app/domain/models.py` 的 pydantic 模型，步与步之间不共享隐式状态。

### 1.3 为什么这样分层

依赖方向**只向下**：`api/`（入口，零业务）→ `orchestrator/`（编排）→ `parsers/ · validators/ · repositories/ · reporters/` → `domain/`（类型即契约）。

- **入口层零业务**：路由只做参数绑定与响应封装，领域错误统一映射到 HTTP 状态码（400 参数校验 / 404 资源不存在 / 409 闸门拦截）。这样「闸门不变量」是服务端强制的，不依赖前端。
- **解析与校验分离**：解析只做模板抽取与归一化，不判定对错；校验只读解析结果与账号表快照，判定异常。职责单一，才可对「归一化写错会静默出错」这类风险写定向变异用例。
- **域模型即契约**：`Anomaly` 是校验层与界面层之间唯一的接口，缺任一证据字段时界面降级显示「证据不完整」——这倒逼解析器必须保留 `source_span`，否则界面无法高亮冲突 token。
- **编排层不感知 HTTP**：`pipeline` 与 `review_gate` 不 import fastapi，便于用 TestClient 之外的纯逻辑测试与复用。

### 1.4 五条基础要求的落地映射

| 题目要求 | 落地 |
|----------|------|
| 1 提取账号、金额、支付人、打款状态等 | `LineItem` + `ClaimSummary` 双模型；金额全程 `Decimal` 保 2 位 |
| 2 写入《推广账号表》测试副本 | 源表只读，`copy_test_copy()` 复制副本再写；13 列按回填权限表逐列约束 |
| 3 汇总当天抖加与垫付金额 | `GET /summary` 返回**三口径并列**，故意不合并 |
| 4 生成负责人简短汇报 | `POST /reports/daily` 产出 markdown 卡片，区分已确认 / 待确认金额 |
| 5 不猜测、标记并提醒人工确认 | 25 个异常码分档，每条带证据与 `action_required`；未裁决 P0 时写表返回 **409** |

## 二、遇到的问题

以下均为**真实记录**，来源：`.workbuddy/memory/2026-09-16.md`、`.workbuddy/memory/pitfalls.jsonl`，以及本仓库联调阶段实测修掉的缺陷。表格格式：现象 → 根因 → 修法。

### 2.1 工程实现类缺陷（联调阶段实测）

| 现象 | 根因 | 修法 |
|------|------|------|
| `GET /api/v1/account-tables/{id}` 直接 500 | `app/orchestrator/pipeline.py` 的 `table_detail()` 引用了**未赋值的变量 `record`**（漏写取数行），运行时 `NameError`；普通单测若未覆盖该端点，不会暴露 | 函数开头补 `record = _require_table(table_id)`；用 `pyflakes` 静态扫描把此类未定义名纳入门禁 |
| 写裁决日志时 `NameError: name 'ev' is not defined` | `app/orchestrator/review_gate.py` 漏导入 `ev`（`from app.domain.enums import ... ev`），只有走到日志落盘的分支才触发 | 补齐导入；`e2e_smoke.py` 增加「导出裁决日志」用例，强制走到该分支 |
| 重跑字段冲突校验时参数个数不匹配报错 | `_field_conflicts` 调用少传 `batch_payer` 参数（真实签名是 5 个参数：`factory, biz_type, batch_payer, items, index`） | 按真实签名补参；统一由编排层提供 `batch_payer` |
| **闸门死锁**：歧义异常用「修正为某值」钉死目标行后，若重跑暴露了**新的 P0**，被 override 的那条仍停留在「未裁决」；操作员解完新异常后它仍 pending，而再次 override 又会不断产出同名新异常 | 原实现把「目标行被钉死」当作**尚未裁决**，把重跑结果与旧异常状态混在一起 | 钉死目标行即视为**该歧义已裁决**（`anomaly.resolved = True`）；重跑暴露的新冲突作为**独立异常**（自带 `anomaly_id`）去阻断；并在 `_pin_ambiguous_target` 里按 `(code, line_no, target_field)` 做**幂等去重**，避免同一冲突反复落条 |
| **跨表写表风险**：用 A 表解析出的行号，可能被写到 B 表的同名行上 | `row_ref`（行号）只在**解析所用的那张表**上有意义，原实现允许提交时换表 | `ParseResult` 增加 `table_id`；`commit_request` 校验「校验所用的表 == 写入目标表」，不一致直接 400 |
| `GET /api/v1/requests/{id}/resolutions` 复核时用错表：「按 A 表判定的异常、用 B 表复核」 | 原实现取的是「默认表」快照，而不是「该申请解析时用的表」的快照 | 改用 `result.table_id` 对应的快照 |
| Python 3.11+ 下 `str(SomeEnum.MEMBER)` 返回 `'SomeEnum.MEMBER'`，污染 JSONL 裁决日志（出现 `AnomalyCode.XXX` 这类字符串） | 枚举直接 `str()` 落盘；3.11 起 `str(IntEnum)` / `str(StrEnum)` 行为变化 | 统一走 `app/domain/enums.py` 的 `ev()` 取 `.value`；模型层把枚举按 str 存储。`e2e_smoke.py` 增加「日志不含枚举对象字面量」断言 |
| 调用上传接口报 `RuntimeError: Form data requires "python-multipart" to be installed.` | FastAPI 使用 `UploadFile` 需要 `python-multipart`，缺依赖 | 加入依赖清单 `python-multipart==0.0.32` |
| **畸形日期输入导致解析端点 500**：非法月日（如 `13/45/99`、`2026/13/01`）令 `POST /api/v1/requests/parse` 返回 **500**，而非 4xx 领域错误 | `app/parsers/normalizer.py` 四处 `date(...)` 构造抛**裸 `ValueError`**；上层 `app/parsers/advance_parser.py` 只捕获 `UnresolvableError`、未兜住 `ValueError`——错误契约不达标 | 四处日期构造全部收敛为 `UnresolvableError`，非法日期遂变为 **HTTP 200 + `DATE_UNRESOLVABLE`（P0 阻断）+ 写表 409**，不再 500；该缺陷先由 `tests/test_normalizer.py` 的 xfail 固化，修复后转为正向断言并补参数化与接口级回归 |

> 上表最后一行是「**AI 生成的代码确有真缺陷，靠测试而非肉眼发现**」的最好例证：这类缺陷只在畸形输入路径触发，通读代码极易放过；把它钉成 xfail 用例后，修复与否由测试机机械判定。

### 2.2 设计与规则类坑（Phase 1 记录，有机械证据）

| 现象 | 根因 | 修法 |
|------|------|------|
| 跨源总额比较被定为 P0 阻断，导致正常批次永远无法落表 | 账号表「抖加」列**没有批次 / 日期维度**，无法证明表内值与该日声明额属于同一批次；且表内累计额必然大于任何单日声明额，阻断会常态化、阈值退化为噪声。该定级还与「抖加批次应零 P0」的自检断言自相矛盾 | 降为 **P1 不阻断**，保留「禁止自动调和、必须人工确认口径」；P0 只留给「同一博主同一字段、文本值与表内已填值不同」这一**可验证**的真冲突。降级后自检一致：抖加批次零 P0、垫付批次 3 个 P0 |
| 界面无法高亮冲突 token，证据对照栏退化为纯文本 | 解析若只保留归一化后的值、不保留原文偏移，界面拿不到冲突位置 | `LineItem` / `ViolationRecord` 必须携带 `source_span`（原文起止偏移）；解析时同步建立偏移映射 |
| 金额比对随机失败、且不可复现 | 金额用 `float` 求和，二进制浮点无法精确表示小数（`0.1 + 0.2 != 0.3` 类），属沉默逻辑错误 | 金额统一 `Decimal` 保 2 位；对金额求和与日期比较写**变异定向**用例（故意写错归一化必须让测试变红） |
| P0 门禁把文档里的勾 / 叉记号（U+2713 / U+2717）判为 emoji | P0-1 的 emoji 正则以 Unicode 区块定义范围（含 U+2700–U+27BF Dingbats），而勾 / 叉记号恰落在该区块内，区块范围宽于「emoji 功能图标」的语义意图 | 文档中改用文字表述（「一致」/「不一致」），不使用勾叉类记号；确需保留时加 `p0-ignore` 行内标记 |
| 门禁把「禁令陈述」误报为违规（如「无 Lorem ipsum」被判命中） | 扫描器不区分上下文，把正当禁令当字面命中。首版把否定窗口设为 14 字仍失败——实测「无 "Welcome to" / "Lorem ipsum"」间距 17 字 | 改为按命中点**前 60 字窗口**检测否定词（无 / 不含 / 禁止 / 不得 / 不出现 / 不使用 / 避免 / 杜绝 / 未出现）；不做「整行出现否定词即豁免」，避免中文文档中「无」字遍地导致漏放 |
| 扫描器把自身正则当作违规 | 扫描器常量里必然写有违禁色值字面量，自扫必然报错，污染门禁输出 | `iter_files` 中排除脚本自身路径；自测一律用独立 fixture 目录并测完清理 |

> 全部修法都用「机械证据」回归：`e2e_smoke.py` 114 条断言、源表 sha256 前后比对、`check_p0.py` 退出码、`pyflakes` 静态扫描。

### 4.2 我做的检查或修改（可核查）

核心态度：**「AI 说什么」不等于「事实成立」**。文档会被改写、代码会漏引用、规则定级可能自相矛盾——所以我坚持**用机械证据去证伪**，而不是靠阅读信任。

1. **端到端回归（断言级）**：`python tools/e2e_smoke.py` → **114/114 全部通过**。它用 TestClient 走完整链路：健康检查 → 登记账号表 → 抖加批次（期望 0 个 P0）→ 垫付批次（期望 3 个 P0）→ 写表应被 409 拦截 → 逐条裁决 → 写表成功 → 幂等重放全 `SKIPPED_ALREADY_WRITTEN` → 当日汇总 → 负责人汇报 → 裁决日志导出。
2. **源表零污染的字节级校验**：比对写入前后源表 `sha256` 必须**不变**；再**逐行逐列**比对测试副本 vs 源表，证明**授权列之外的列零改动**（「报价」列永不写入）。这一步就是用来证伪「我只写了该写的列」这种口头承诺的。
3. **设计红线门禁**：`python tools/check_p0.py docs web` → 退出码 0。扫三类红线（禁 emoji 图标 / 禁紫粉渐变 / 禁模板味文案）。并且对门禁本身做了**反向自测**：注入真实违规的 fixture 必须命中（否则「误报消失」不代表「不误报」）。
4. **静态扫描抓未定义名**：用 `pyflakes` 扫描 `app/ tools/ tests/`，**正是靠它抓到** `pipeline.table_detail()` 的未赋值 `record` 与 `review_gate` 缺失的 `ev` 导入这两个会在运行时抛 `NameError` 的缺陷——这类缺陷单靠通读极易漏掉。
5. **人工复核并逐个修掉**第二节「遇到的问题」列出的全部缺陷**：包括闸门死锁、跨表写表风险、复核用错表、枚举字符串污染日志、缺依赖等。每修一项，都在 `e2e_smoke.py` 中补一条能**强制走到该分支**的断言，避免「改了但没测到」。
6. **口径裁决**：人工查出架构文档自相矛盾（§2.5 说抖加应零 P0，§4.1 却把跨源总额差定为 P0 阻断），裁决**降为 P1** 并同步 PRD / Spec / 测试三处——因为对一个**无法验证的等式**施加阻断，会让正常申请永远无法落表。
7. **范围核对**：核对 AI 是否「越界实现了题目没要求的东西」，并把不做项逐条写进 Spec §3（含原因），锁定范围。
8. **代码量纪律核对（一处自我更正）**：初评时按**总行数**量行数，误把 `validators/cross_check.py` 349 行、`orchestrator/pipeline.py` 347 行、`domain/models.py` 314 行判为超限。经与团队规范对齐口径——「单文件 ≤ 300 行」为**不含空行与注释**的代码行——按正确口径重算，三者分别为 **298 / 275 / 195** 代码行，**均合规**。按同一口径复核 `app/` 与 `tools/` 全部源文件：**无文件超过 300 代码行**，最大者为 `app/validators/cross_check.py`（298 代码行）。此前的「待重构」结论**撤回**。（这一条也说明：文档里每个数字都要用**统一、可复现**的口径核对，口径不一致会制造假问题；首次用错口径时我未与规范原文核对，属我的疏漏。）

## 五、面试演示脚本（从启动到点完 12 步）

```bash
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# 打开 http://127.0.0.1:8000/
```

| 步骤 | 操作 | 这一步证明什么 |
|------|------|----------------|
| 1 | 打开首页，看顶部「测试副本 · 未污染原表」 | 产品定位与不污染原表的承诺 |
| 2 | 看「申请文本」区的系统承诺边栏 | 界面常驻声明「不猜测」（缺失 / 冲突字段不默认填充） |
| 3 | 选「抖加申请」，点「填充示例」 | 载入物料原文，演示可复现、不靠手打 |

## 5. 生产就绪度自评（按团队记分卡）

> 依据：`references/01-standards/production-readiness-scorecard.md`（七维 × Bronze/Silver/Gold，**总档取各维度最低档**，商业级最低线 Silver）。

**缺陷跟踪（曾影响定档，现已修复）**：`app/parsers/normalizer.py` 原对畸形两位年份日期（如 `13/45/99`）抛裸 `ValueError` → `POST /api/v1/requests/parse` 返回 500（错误契约不达标）；修复后非法日期返回 **HTTP 200 + `DATE_UNRESOLVABLE`（P0 阻断）+ 写表 409**，不再 500。
定档口径（记分卡裁决归属测试负责人）：该缺陷**属 P1、非 P0**（不阻塞核心流程、不产生错误写入、不丢数据，仅畸形输入触发）。修复前它只把「契约」维**封顶在 Silver**（不是 Bronze）；**该封顶现已随修复解除**，契约维仍为 Silver，差距转为「契约破坏未在 CI 即红 + 无版本 / 弃用策略」。

**总档 = 各维度最低档 = 低于 Bronze。** 结论：当前为 **demo 级**（能演示、不可托付生产），**未达商业级最低线 Silver**。

### 已知真实短板（如实列出）

1. **主数据在内存**：`app/repositories/memory_store.py` 的 `STORE` 单例，**进程重启即丢**；仅裁决日志 append-only 落 `decisions/decisions.jsonl`（默认在仓库 `data/` 下，可用 `MST_DATA_DIR` 重定向）。持久化只覆盖了审计轨迹，不覆盖主数据。
2. **无鉴权、无用户体系**：演示态单台，任何调用方都能读写。
3. **无并发控制 / 加锁**：两个请求同时写同一副本存在**竞态**（openpyxl 读改写非原子）。
4. **LLM 旁路默认关闭**：无 `LLM_API_KEY` 时自动降级为 no-op；生产化需补**密钥管理与输入脱敏**后再启用。
5. **无 CI、无覆盖率报告**：已有 pytest 套件与 `tools/e2e_smoke.py`、`tools/check_p0.py`，但均为**手动运行**，未接入流水线，也无覆盖率报告。

### 上线前必须最先补（按优先级）

1. 鉴权 / 授权 + 主数据持久化（否则重启即丢数据）。
2. 并发控制：对副本写入串行化 / 加锁。
3. CI 门禁：`pytest` + `tools/e2e_smoke.py` + `tools/check_p0.py` + 覆盖率。
4. 可观测：指标暴露 + SLI/SLO + 告警。
5. 发布安全：CI/CD 流水线 + 备份 + 回滚演练。

> 一句话答辩：**这个 demo 在「单机、单人、内存态、无并发」的演示条件下可用；只要进入「多人 / 多请求并发 / 需跨重启保留主数据 / 需对外暴露」任一条件，就必须先补上面的 1–5，否则不能上线。**
