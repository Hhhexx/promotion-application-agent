# 02 架构设计 —— 推广申请处理 Agent（演示态）

> 版本：v1.0 | 阶段：Phase 1 技术调研与契约设计 | 面向：前后端实现者、QA、面试答辩
> 本文是**规格即契约**（spec-as-contract）意义上的执行契约：点名文件与接口、钉死范围与版本、内嵌已知坑、以端到端验证步骤收尾。

## 0. 范围声明（out-of-scope，先说不做什么）

本次交付**只覆盖演示态**，以下明确**不做**：

| 不做项 | 原因 |
|---|---|
| 真实 IM / 企业微信 / 飞书 消息接入 | 演示态用「粘贴文本 / 上传 txt」替代，接入属生产化缺口 |
| 用户鉴权、多用户、角色权限（RBAC） | 单机单用户演示，无登录 |
| 对**生产**《推广账号表》的任何写入 | 只写测试副本；生产表只读且不在仓库内 |
| 真实数据库 / 持久化 / 消息队列 / 定时任务 | 演示态用内存 + 临时 xlsx 副本 |
| 自动"猜"博主归属、自动新建表格行、自动改写人工字段 | 题目第 5 条硬约束：禁止猜测，必须人工确认 |
| LLM 作为**必需**依赖 | LLM 为可选旁路，无密钥也必须完整跑通 |
| 移动端 / 小程序 / 多端适配 | 单页 Web 操作台（桌面优先） |

**原子写入策略禁止清单（架构级硬约束，实现违反即不合格）：**

1. 禁止任何绕过人工确认闸门的自动写表动作（新增/更新账号表记录）。
2. 禁止把「抖加金额」写入「报价」字段（两者是不同概念，见 §3.3）。
3. 禁止在字段缺失、匹配歧义、日期或汇总不一致时自动补默认值。
4. 禁止覆盖账号表已有的非空人工字段（`类型 / 报价 / 发布日期 / 是否接单 / 审核结果` 等）。

## 1. 技术选型对比矩阵

### 1.1 候选方案

| 编号 | 方案 | 形态 |
|---|---|---|
| 方案 A | 单体 Python 服务 + 规则解析引擎（确定性工作流） | FastAPI + 自研 parser/validator 规则管线 |
| 方案 B | LLM 抽取为主（LangChain / LangGraph 类框架编排） | 由 LLM 承担字段抽取与决策，框架做 chain/graph |
| 方案 C | 低代码 / 工作流编排平台（n8n / Dify / 扣子 Coze） | 可视化节点编排，平台托管运行 |
| 方案 D（目标） | 方案 A 为主干 + LLM 作为**可选**交叉校验旁路 | A 的确定性管线 + 可插拔 LLM adapter |

### 1.2 评分矩阵（1-5 分，5 = 最优）

| 维度 | 权重 | A 单体+规则 | B LLM 抽取为主 | C 低代码编排 |
|---|---|---|---|---|
| 可复现性（同输入同输出） | 高 | 5 | 2 | 3 |
| 离线可跑（无网络/无密钥） | 高 | 5 | 1 | 2 |
| 面试演示说服力（可解释/可讲清核心代码） | 高 | 5 | 3 | 2 |
| 开发成本（越低越高分） | 高 | 4 | 3 | 5 |
| 出错可解释性（能定位到规则/行） | 高 | 5 | 2 | 2 |
| 依赖风险（越低越高分） | 高 | 5 | 2 | 2 |
| 契合「不猜测」硬约束 | 高 | 5 | 2 | 3 |
| 扩展性（未来接 IM/多表） | 低 | 4 | 4 | 4 |
| **加权结论** | | **首选主干** | 备选 | 演示可用但不可控 |

> 评分为**相对排序**，非绝对度量；权重取「学习成本/生态/部署/可解释/团队熟悉度」中对本题最关键的几项（见 `references/architecture/mvp-stack.md` 的选型维度）。

### 1.3 结论：收敛到方案 D（= 用户已定方案）

- **主干采用方案 A**：确定性规则管线。理由：本题输入格式高度模板化、输出结构固定、校验规则可枚举，确定性管线在**可复现 / 离线 / 可解释 / 可测试**四项全占优，且天然满足「不猜测」。
- **方案 B 降级为可选旁路**：LLM 只在「规则低置信行」与「语义交叉校验」两处接入，**不一致即升级人工**，绝不替代规则主干。
- **方案 C（低代码）不采用**：可视化的代价是「逻辑藏在平台里」，面试无法讲清核心代码，且平台运行时不可控、离线不可跑、导出流程难复现；作为演示也不如自研管线能体现工程判断。

### 1.4 方案 D 的真实风险与缓解（必须写明的 2-3 个）

| 风险 | 具体表现 | 影响 | 缓解措施 |
|---|---|---|---|
| R1 规则脆性（模板漂移） | 申请文本模板一旦改动（换措辞、加字段、换全角符号），正则/模式失配 → 该行解析失败 | 高：解析召回下降 | ① 解析失败**不静默跳过**，一律产出 P0「未解析行」异常交人工；② 每条规则带「样本回归用例」，模板变更即回归红灯；③ LLM 旁路仅在低置信时兜底提示，不自动采纳 |
| R2 LLM 旁路引入非确定性 | 开启 LLM 后同输入结论漂移，破坏可复现性 | 中：演示与回归不一致 | ① LLM 结果**只做交叉校验**，与规则不一致 → 升级人工（不采用其值）；② LLM 默认关闭，回归测试集**禁用** LLM；③ adapter 记录每次调用的模型名/版本/入参摘要用于审计 |
| R3 日期与金额归一化的静默逻辑错误 | `4.9` 缺年份、`26/08/31` 两位数年份、`¥` 与千分位符号，归一化写错时**不报错只算错** | 高：属于最致命的「沉默逻辑错误」 | ① 日期归一化**必须带上下文年份**，无法唯一确定 → P0 不猜；② 金额统一 `Decimal` 保 2 位，禁止 float；③ 对金额求和/日期比较写**变异定向**用例（见 §8），归一化写错必须变红 |

## 2. 数据契约设计（本阶段最高优先级）

> 设计原则：**行级「申请条目」与表级「汇总声明」分开建模**。文本里既有明细行，也有「今日共 N 笔 / 已支付 ¥X」这类**汇总声明**，两者必须分别建模，才能做交叉校验（第 5 条要求发现「总额不一致」）。

### 2.1 公共枚举

| 枚举 | 取值 | 说明 |
|---|---|---|
| `BizType` | `doujia` / `advance` | 抖加申请 / 垫付申请 |
| `Severity` | `P0` / `P1` / `P2` | 阻断 / 警告 / 提示 |
| `AnomalyCode` | 见 §4 异常码表 | 机器可判定的异常标识 |
| `ItemState` | `PARSED / NEEDS_REVIEW / RESOLVED / READY / WRITTEN / SKIPPED / BLOCKED` | 条目状态，见 §6 |

### 2.2 模型一：申请条目（`LineItem`，行级）

字段来源为文本「明细如下：」后的每一行。抖加与垫付共用基类，类型特化字段以 `*` 标注。

| 字段名 | 含义 | 类型 | 必填 | 来源文本模式（抖加 / 垫付） | 归一化规则 | 校验规则 |
|---|---|---|---|---|---|---|
| `line_no` | 原文行号（1 起） | int | 是 | 全文计数 | 无 | 唯一 |
| `biz_type` | 申请类型 | `BizType` | 是 | 由文档头判定 | 无 | 枚举内 |
| `blogger_name_raw` | 博主昵称原始值 | str | 是 | 抖加：`博主名：(.+?)\s*-\s*金额`；垫付：`【达人：(.+?)】` | 仅去首尾空白 | 非空；禁止语义改写 |
| `blogger_name_norm` | 昵称归一值 | str | 是 | 由 raw 派生 | NFKC + 去零宽 + 折叠空白 + ASCII 小写 | 非空 |
| `song_name` | 歌名 | str | 否 | 抖加：`歌名：《(.+?)》`；垫付：`（歌曲《(.+?)》）` | 去首尾空白 | 若存在则非空 |
| `amount` | 金额 | `Decimal(12,2)` | 是 | 抖加：`金额：¥(\d+(?:\.\d+)?)`；垫付：`垫付 ¥(\d+(?:\.\d+)?)` | 去 `¥`/`,`，转 Decimal 保 2 位 | > 0；解析失败 → P0 |
| `split_count` * | 分笔数（仅抖加） | int | 否 | `（分 (\d+) 笔）` | 默认 1 | ≥ 1 |
| `payer` | 支付人 / 打款人 | str | 是 | 抖加：文末 `抖加支付人：(.+)`；垫付：`打款人：(.+)` | 去首尾空白 | 非空 |
| `request_date` | 申请日期 | date | 是 | 文档头 `（YYYY-MM-DD）` | 归一 ISO | 可解析；与文档头一致 |
| `source_span` | 原文起止偏移 | `[int,int]` | 是 | 解析时记录 | 无 | 可定位回原文 |
| `dedup_key` | 幂等/去重复合键 | str | 是 | 由归一字段拼装 | 见 §2.6 | 唯一性参与重复检测 |
| `match_result` | 表匹配结果 | `MatchResult` | 否 | 匹配阶段产出 | 见 §2.7 | 决定是否可自动回填 |

### 2.3 模型二：汇总声明（`ClaimSummary`，表级）

文本里以自然语言给出的「整批」**声明**，独立于明细行建模，用于交叉校验。

| 字段名 | 含义 | 类型 | 必填 | 来源文本模式 | 备注 |
|---|---|---|---|---|---|
| `biz_type` | 申请类型 | `BizType` | 是 | 文档头 | |
| `declared_total_amount` | 声明总额 | `Decimal(12,2)` | 是 | 抖加：`今日已支付：¥(\d+)`；垫付：`今日已垫付：¥(\d+)` | 与明细求和比对 |
| `declared_date` | 声明日期 | date | 是 | `（YYYY-MM-DD）` | 与预计打款日期比对 |
| `declared_count` | 声明笔数 | int | 否 | `今日共 (\d+) 笔` | 与 `sum(split_count)` 比对 |
| `declared_merged_count` * | 声明合并后笔数 | int | 否 | 抖加：`合并同博主后为 (\d+) 笔` | 与明细行数比对 |
| `payer` | 支付人 / 打款人 | str | 是 | 文末 | 与条目的 payer 一致性校验 |
| `expected_pay_date` * | 预计打款日期（仅垫付） | date | 否 | `预计打款日期：(\d{2}/\d{2}/\d{2})` | 与 `declared_date` 比对 → 日期异常 |

### 2.4 模型三：解析产物（`ParseResult`）

```
ParseResult
├─ request:      RequestHeader   # request_id, biz_type, declared_date, source_type(text|file), raw_text
├─ summary:      ClaimSummary    # 表级汇总声明
├─ line_items:   LineItem[]      # 行级申请条目
├─ anomalies:    Anomaly[]       # 全部异常（分级）
└─ cross_check:  CrossCheck      # 交叉校验明细（见 §2.5）
```

### 2.5 交叉校验（`CrossCheck`）——「不猜测」的核心判定

| 校验项 | 判定 | 不一致时异常 |
|---|---|---|
| 明细求和 vs 声明总额 | `sum(item.amount) == summary.declared_total_amount` | `TOTAL_MISMATCH`（P0） |
| 分笔数求和 vs 声明笔数 | `sum(item.split_count) == summary.declared_count` | `COUNT_MISMATCH`（P0） |
| 明细行数 vs 声明合并笔数 | `len(line_items) == summary.declared_merged_count` | `MERGED_COUNT_MISMATCH`（P1） |
| 预计打款日 vs 申请日 | `expected_pay_date >= declared_date` | `DATE_ORDER_INVALID`（P0） |
| 各条目 payer vs 汇总 payer | 全部相等 | `PAYER_INCONSISTENT`（P1） |
| **跨源**：文本声明总额 vs 表内对应列求和 | 相等（如抖加：文本 700 vs 表内「抖加」列求和） | `CROSS_SOURCE_TOTAL_MISMATCH`（P1，**不阻断**，口径待人工确认） |
| **跨源**：文本明细博主 vs 表内对应列 | 文本抖加明细博主集合与表内「抖加」列非空博主集合一致 | `CROSS_SOURCE_SCOPE_MISMATCH`（P1） |
| **跨源**：文本单值字段 vs 表内对应记录取值 | **同一博主、同一字段**且文本值与表内已填值不同（如某博主文本支付人 X vs 表内该行支付人 Y） | `CROSS_SOURCE_FIELD_CONFLICT`（P0） |

> **跨源判定的因果边界（重要）：** 账号表「抖加」列**没有批次/日期维度**，无法证明表内累计额与某单日声明额属于同一批次，故两者不等**不构成正确性缺陷**，只作口径待确认（P1，不阻断）。而 `CROSS_SOURCE_FIELD_CONFLICT`（P0）**仅在"同一博主同一字段、文本值与表内已填值不同"时成立**——物料里「文本支付人=爆火音乐 vs 表内**高高**=李老师」**不满足**该条件（高高不在本批文本明细内，不同博主由不同人支付可并存），该情形归入 `CROSS_SOURCE_SCOPE_MISMATCH`（P1），不升格 P0。

> **物料自检结论（架构师依据物料人工推演，经项目总监复核，供 QA 交叉验证）：**
> - **抖加申请（2026-09-02）**：明细 300+200+100+100 = 700，与声明 `¥700` **一致**；分笔 3+2+1+1 = 7，与声明「共 7 笔」**一致**；合并后 4 笔 = 4 行 **一致**；4 位博主在表内各唯一命中 1 行、无行内 dedup 冲突。→ **零 P0**（会产 P1：跨源口径待确认 `CROSS_SOURCE_TOTAL_MISMATCH` 700 vs 表内 400、`CROSS_SOURCE_SCOPE_MISMATCH`，均不阻断）。
> - **垫付申请（2026-09-03）**：明细 950+300+300+200+500 = 2250，与声明 `¥2250` **金额一致**；但声明「共 7 笔」vs 明细 5 行 → `COUNT_MISMATCH`（P0）；`预计打款日期 26/08/31` 早于申请日 `2026-09-03` → `DATE_ORDER_INVALID`（P0）；「葵花夫妇」在表内 2 行 → `MATCH_AMBIGUOUS`（P0）。→ **3 个 P0**，满足 ≥2 断言。
> 该结论是 §6 端到端验证的断言基线。

### 2.6 去重与幂等键

**复合键（规范化后拼装）：**

```
dedup_key = f"{biz_type}|{request_date_iso}|{blogger_name_norm}|{amount:0.2f}|{payer_norm}"
```

示例：`advance|2026-09-03|葵花夫妇|500.00|林老师`

**规范化步骤（按序执行，全程确定性、可单测）：**

1. `Unicode NFKC` 归一：全角转半角（`¥`→`¥` 语义统一、`（）`→`()`、全角字母数字→半角）。
2. 去除零宽字符（`\u200b-\u200f\u2060\ufeff`）与控制字符。
3. 折叠连续空白为单空格并去首尾。
4. ASCII 段转小写；CJK 段保持不变（**不做**拼音/简繁转换——那属于猜测）。
5. 金额：去除 `¥` 与千分位 `,`，`Decimal` 量化到 2 位。
6. 日期：归一为 ISO `YYYY-MM-DD`，两位数年份按「距离声明年份最近」的确定性规则补全（`26/08/31` → `2026-08-31`），补全规则**必须记录在审计字段**。
7. **禁止**的"归一"：去昵称装饰后缀（如 `（虾仁）`）、去前缀 `@@`、同义昵称合并——这些是语义猜测。

**幂等语义：**

- 同一 `dedup_key` 在**同一请求内**重复出现 → `DUPLICATE_WITHIN_REQUEST`（P0，重复申请）。
- 同一 `dedup_key` 在**已写入的测试副本**中已存在 → 提交阶段判重，返回 `SKIPPED_ALREADY_WRITTEN`（幂等，不重复写、不报错）。
- **批次级幂等键（与 PRD AC-08 对齐）：** 提交以 `batch_id = f"{biz_type}|{request_date_iso}"` 为批次锁，二次提交同批次命中即整体跳过；条目级 `dedup_key` 为**细粒度补充**，二者共同保证"同批次重复点击不产生重复行"。

### 2.7 归一化与模糊匹配策略（候选匹配，禁止猜测）

博主昵称在文本与表格间可能不一致（文本「葵花夫妇」对应表中**两行**；表内存在空抖音号行）。匹配采用**分级 + 升级人工**：

| 级别 | 条件 | 置信 | 处置 |
|---|---|---|---|
| `EXACT_ID` | 抖音号归一后唯一命中 | 高 | 可作自动回填目标 |
| `EXACT_NAME` | 昵称归一后**恰好 1 行**命中 | 高 | 可作自动回填目标 |
| `AMBIGUOUS` | 昵称归一后**命中 ≥2 行**（如葵花夫妇） | 无法判定 | P0 `MATCH_AMBIGUOUS` → 人工选行 |
| `NO_MATCH` | 无任何命中 | 无法判定 | P0 `MATCH_NOT_FOUND` → 人工处理（**禁止自动新建行**） |
| `WEAK_FUZZY` | 编辑距离/`difflib` 相似度生成**候选**但未过严格阈值 | 低 | 仅作为**候选提示**送人工，**不自动采用** |

`MatchResult` 结构：`{ level, matched_row_ref?, candidates: [{row_ref, name, douyin_id, score}], note }`

> **明确禁止（架构级硬约束）：** 任何形式的兜底猜测——无匹配时自动创建新行、多匹配时按"第一个/最高分"自动选、昵称模糊时自动合并。所有非 `EXACT_*` 情形**一律**升级人工确认。

## 3. 账号表字段映射与回填规则

### 3.1 账号表 13 字段（物料 C）

`类型 | 抖音昵称 | 抖音号 | 报价 | 抖加 | 抖加支付人 | 是否打款 | 打款人 | 打款日期 | 发布日期 | 是否接单 | 审核结果 | 备注`

### 3.2 字段映射与回填权限表

| # | 表字段 | 英文键 | 来源 | 回填权限 | 说明 |
|---|---|---|---|---|---|
| 1 | 类型 | `type` | 表内已有 | **禁止**自动写/改 | 申请文本不含类型；新建行时必须人工填 |
| 2 | 抖音昵称 | `douyin_nickname` | 文本 | **禁止覆盖**，仅核对 | 匹配到已有行时不覆盖；作为匹配依据 |
| 3 | 抖音号 | `douyin_id` | 文本无 | **禁止**自动写 | 文本未提供；留空 |
| 4 | 报价 | `quote_price` | 文本无 | **禁止**写 | 见 §3.3 硬约束 |
| 5 | 抖加 | `doujia_amount` | 抖加申请 `amount` | **可回填**（需人工确认闸门通过） | 默认追加/填空白格；已有非空值 → P1 提示不覆盖 |
| 6 | 抖加支付人 | `doujia_payer` | 抖加申请 `payer` | **可回填**（同上） | 已有非空值 → P1 提示不覆盖 |
| 7 | 是否打款 | `is_paid` | 垫付申请推断 | **人工确认后**才可写 | 默认 `待确认` |
| 8 | 打款人 | `payer` | 垫付申请 `payer` | **人工确认后**才可写 | |
| 9 | 打款日期 | `pay_date` | 垫付 `expected_pay_date` | **人工确认后**才可写 | 日期异常时更要人工 |
| 10 | 发布日期 | `publish_date` | 文本无 | **禁止**自动写 | |
| 11 | 是否接单 | `accepted` | 文本无 | **禁止**自动写 | |
| 12 | 审核结果 | `review_result` | 文本无 | **禁止**自动写 | |
| 13 | 备注 | `remark` | 系统 | **系统可写** | 写入审计备注：`来源=<biz_type>@<date>；batch_id=...；request_id=...；rule_id=...；确认人=...；时间=...` |

> **测试副本写入策略（已定档，与 PRD AC-09 / R-05 对齐，见 OPEN-DECISIONS 关闭记录）：** **追加 + 溯源列**——原表只读，副本保留每次写入轨迹，不用覆盖（覆盖会破坏可追溯性）。溯源列以**下划线前缀**标识系统列（`_batch_id / _request_id / _rule_id / _confirmed_by / _confirmed_at / _dedup_key`），与业务 13 列并存、不污染业务字段。源表只读，副本复制后再写。

### 3.3 硬约束：抖加金额 ≠ 报价

> 「报价」是博主**合作报价**，「抖加」是**抖加流量券费用**，二者语义与数值均不同（物料字段说明明确区分）。
> **禁止**将抖加申请的金额写入「报价」列，也禁止反向。实现层对 `quote_price` 字段设**只读**语义，任何写入路径直接抛错（该错误在测试中必须被覆盖）。

### 3.4 「人工确认后才可写」字段的落表条件

`is_paid / payer / pay_date` 三字段的写入前置条件（三者同时满足才执行写入）：

1. 该条目**无未裁决的 P0 异常**；
2. 存在一条**人工裁决记录**（`decision ∈ {accept, override}`）且带确认人标识与时间戳；
3. 写前对目标单元格做「非空检测」：若已有非空值且与待写值不同 → 不覆盖，改为 P1 提示。

## 4. 异常分级与人工确认闸门

### 4.1 异常码表

| 异常码 | 级别 | 触发条件 | 是否阻断写表 |
|---|---|---|---|
| `TOTAL_MISMATCH` | P0 | 明细金额求和 ≠ 声明总额 | 是 |
| `COUNT_MISMATCH` | P0 | `sum(split_count)` ≠ 声明笔数 | 是 |
| `FIELD_MISSING` | P0 | 必填字段缺失（博主/金额/支付人/日期） | 是 |
| `UNPARSED_LINE` | P0 | 明细行无法被任何规则模式解析 | 是 |
| `DATE_ORDER_INVALID` | P0 | 预计打款日期 < 申请日期 | 是 |
| `DATE_UNRESOLVABLE` | P0 | 日期无法唯一归一（如 `4.9` 缺年份且上下文不足） | 是 |
| `DUPLICATE_WITHIN_REQUEST` | P0 | 同请求内 `dedup_key` 冲突 | 是 |
| `MATCH_AMBIGUOUS` | P0 | 昵称命中 ≥2 行 | 是 |
| `MATCH_NOT_FOUND` | P0 | 无任何命中 | 是 |
| `LLM_RULE_CONFLICT` | P0 | LLM 交叉校验与规则结果不一致 | 是 |
| `MERGED_COUNT_MISMATCH` | P1 | 明细行数 ≠ 声明合并笔数 | 否（标注后可写） |
| `PAYER_INCONSISTENT` | P1 | 条目 payer 与汇总 payer 不一致 | 否 |
| `TARGET_CELL_NONEMPTY` | P1 | 目标单元格已有非空值 | 否（不覆盖，提示） |
| `DATE_FORMAT_INCONSISTENT` | P1 | 表内日期格式混杂（`4.9`/`4.10`/`2026/8/21`） | 否 |
| `DOUYIN_ID_EMPTY` | P1 | 匹配行抖音号为空，仅靠昵称匹配 | 否 |
| `CROSS_SOURCE_TOTAL_MISMATCH` | P1 | 文本声明总额 ≠ 表内对应列求和（如抖加 700 vs 表内 400）；表内列无批次维度，属口径待确认而非正确性缺陷 | 否（禁止自动调和，标注待人工确认） |
| `CROSS_SOURCE_FIELD_CONFLICT` | P0 | **同一博主同一字段**且文本值与表内已填值不同 | 是 |
| `CROSS_SOURCE_SCOPE_MISMATCH` | P1 | 文本明细博主集合与表内对应列非空博主集合不一致（含"文本值所在博主不在本批明细内"的情形） | 否 |
| `STATUS_FIELD_INCONSISTENT` | P1 | `是否打款=是` 但 `打款人/打款日期` 为空；或 `抖加>0` 但 `抖加支付人` 空 | 否 |
| `UNACCEPTED_WITH_AMOUNT` | P1 | `是否接单=否` 却存在金额 | 否 |
| `DOUJIA_EXCEEDS_QUOTE` | P2 | 抖加 > 报价（报价非空时），费用异常偏高 | 否 |
| `NICKNAME_DIRTY` | P2 | 昵称含非业务字符（如 `@@` 前缀） | 否 |
| `SPLIT_NOT_RETAINED` | P2 | 含「分 N 笔」但未保留分笔信息 | 否 |
| `TABLE_EMPTY_ROW_SKIPPED` | P2 | 表内空行被跳过 | 否 |
| `REMARK_EMPTY` | P2 | 备注为空 | 否 |

### 4.2 处理链路（确定性）

```
parse ──→ validate ──→ 生成 anomalies(P0/P1/P2)
                              │
        ┌─────────────────────┴─────────────────────┐
        │ 存在 P0                                    │ 无 P0
        ↓                                            ↓
  该条目/整批置 NEEDS_REVIEW                  置 READY（P1/P2 仅标注）
  禁止写表；写表接口对该条目返回 409         可进入写表
        │
        ↓
  人工在操作台逐条裁决：accept(采纳建议) | override(修正值) | ignore(忽略该条)
        │
        ↓
  裁决后对该条**重新校验**（规则重跑）
        │
  通过 ──→ RESOLVED ──→ READY ──→ 写表(幂等, dedup 判重) ──→ WRITTEN ──→ 回读校验 VERIFIED
  仍失败 ──→ 保持 NEEDS_REVIEW（回到裁决）
```

### 4.3 状态流转（`ItemState`）

```
PARSED → VALIDATING → ┬─ NEEDS_REVIEW ─(裁决)→ RESOLVED → READY
                      └─ READY ─(写表)→ WRITING → WRITTEN → VERIFIED
                                                   └(dedup 命中)→ SKIPPED_ALREADY_WRITTEN
```

**闸门不变量（invariant）：** 任何 `WRITTEN` 之前必须经过 `READY`；任何 `READY` 必须无未裁决 P0。写表接口对含未裁决 P0 的请求返回 HTTP `409`。

### 4.4 与 PRD 异常编号（EXC-xx）的对齐

PRD（`01-PRD-推广申请处理Agent.md`）以 `EXC-01`~`EXC-16` 面向产品描述异常。二者关系：`EXC-xx` 是**产品可读编号**，本文机器码是**代码级枚举**，同一条规则两个名字。实现时以机器码为准，`Anomaly` 上同时携带 `exc_id` 便于与 PRD 对齐。

| PRD 编号 | 异常名称 | 本文机器码 | 级别 |
|---|---|---|---|
| EXC-01 | 笔数口径不自洽 | `COUNT_MISMATCH` | P0 |
| EXC-02 | 日期倒挂 / 跨年 | `DATE_ORDER_INVALID` / `DATE_UNRESOLVABLE` | P0 |
| EXC-03 | 金额口径不一致 | `TOTAL_MISMATCH`（P0） / `CROSS_SOURCE_TOTAL_MISMATCH`（P1） | P0 / P1 |
| EXC-04 | 重复申请 / 目标不唯一 | `DUPLICATE_WITHIN_REQUEST` / `MATCH_AMBIGUOUS` | P0 |
| EXC-05 | 跨源字段取值冲突（同博主同字段） | `CROSS_SOURCE_FIELD_CONFLICT`（P0，条件收紧：仅同一博主同一字段值不同） | P0 |
| EXC-06 | 实体匹配不唯一 / 缺失 | `MATCH_AMBIGUOUS` / `MATCH_NOT_FOUND` | P0 |
| EXC-07 | 状态与字段不自洽 | `STATUS_FIELD_INCONSISTENT` | P1 |
| EXC-08 | 整行 / 主键空行 | `TABLE_EMPTY_ROW_SKIPPED` | P1 |
| EXC-09 | 未接单却产生金额 | `UNACCEPTED_WITH_AMOUNT` | P1 |
| EXC-10 | 日期格式不统一 | `DATE_FORMAT_INCONSISTENT` | P1 |
| EXC-11 | 抖加列与文本明细交叉不匹配 | `CROSS_SOURCE_SCOPE_MISMATCH` | P1 |
| EXC-12 | 抖加金额超过报价 | `DOUJIA_EXCEEDS_QUOTE` | P2 |
| EXC-13 | 接单与审核状态矛盾 | `STATUS_FIELD_INCONSISTENT` | P2 |
| EXC-14 | 备注被标记但内容为空 | `REMARK_EMPTY` | P2 |
| EXC-15 | 昵称含特殊字符 | `NICKNAME_DIRTY` | P2 |
| EXC-16 | 分笔申请未留存子明细 | `SPLIT_NOT_RETAINED` | P2 |

**本锚点的用法（Spec / OpenAPI / 测试用例三处统一）：** 此表是 `EXC-xx`（产品编号，PRD 侧）与异常码 enum（代码侧，OpenAPI 侧）之间的**唯一映射源**。多对一允许（一个 `EXC` 可映射多个 code）；以下 code **无 PRD 的 EXC 对应项**，属架构侧新增，PRD 侧可引用其机器码：`FIELD_MISSING`、`UNPARSED_LINE`、`MERGED_COUNT_MISMATCH`、`PAYER_INCONSISTENT`、`TARGET_CELL_NONEMPTY`、`LLM_RULE_CONFLICT`、`DOUYIN_ID_EMPTY`、`STATUS_FIELD_INCONSISTENT`（与 EXC-13 共用）。测试用例命名建议 `test_<code>__exc<N>`，双向可搜。

### 4.5 异常定档原则（P0 阈值边界）——跨源降级的理由（可直接答辩）

**P0 阻断只允许用于三类问题**，其余一律 P1/P2：

1. **正确性缺陷**：同一数据源内部自相矛盾、可被确定性判定的错误（如 `TOTAL_MISMATCH` 明细求和≠同文声明总额、`COUNT_MISMATCH`、`DATE_ORDER_INVALID`）。
2. **需求未满足**：解析不出必填字段（`FIELD_MISSING`、`UNPARSED_LINE`）、无法确定写入目标（`MATCH_AMBIGUOUS`、`MATCH_NOT_FOUND`）。
3. **契约安全 / 数据完整性破坏**：会污染表或破坏幂等（`DUPLICATE_WITHIN_REQUEST`、同记录同字段冲突 `CROSS_SOURCE_FIELD_CONFLICT`、`LLM_RULE_CONFLICT`）。

**为何 `CROSS_SOURCE_TOTAL_MISMATCH` 必须降为 P1（不阻断）：**

- 账号表「抖加」列**没有批次或日期维度**，无法证明"表内累计 400"与"文本单日声明 700"属于**同一批次**——这是一个**无法验证的等式**，把它当作正确性缺陷属于误判。
- 若据此阻断，**表内累计额必然大于任何单日声明额**，则每一批正常申请都将永久无法落表，**阻断常态化即等于阈值失效**。这不是"更安全"，是把阻断阈值设成了噪声。
- 降级后语义保留：仍**禁止自动调和**（不得把 400 改成 700 或反之），仅**标注口径待人工确认**，写入照常进行。

**自检复核（项目总监已核，架构师确认）：** 降级后 —— 抖加批次**零 P0**（仅 P1 跨源口径提示）；垫付批次 **3 个 P0**（`COUNT_MISMATCH` + `DATE_ORDER_INVALID` + `MATCH_AMBIGUOUS`）。两处断言与 §2.5、§6 一致。

### 5.3 编排形态论证（单体 Agent vs 多 Agent vs 普通工作流）—— 可直接用于面试答辩

**结论：采用「普通工作流（确定性管线）+ 可选 LLM 单点旁路」。既不是单体 Agent，也不是多 Agent。**

| 维度 | 单体 Agent（自主 ReAct/工具调用） | 多 Agent（分工协作） | 普通工作流（本题选定） |
|---|---|---|---|
| 可复现性 | 低（LLM 自主路径漂移） | 低（多体协商更不可控） | **高**（步进确定性） |
| 可解释性 | 低（结论来自模型） | 低 | **高**（每步可日志、可定位到行/规则） |
| 契合「不猜测」 | 差（自主性即猜测温床） | 差 | **好**（校验规则显式枚举） |
| 离线可跑 | 差（强依赖 LLM） | 差 | **好**（纯规则，无网络） |
| 开发成本 | 中（要调 prompt/工具） | 高（编排+协调） | **低**（规则直接可测） |
| 复杂度 | 中 | 高（过度设计） | **低** |

**判定逻辑（三条）：**

1. **任务性质决定形态。** 本题输入是**模板化文本**、输出是**固定结构表行**，判定规则（总额/笔数/日期/重复）**可枚举**——这是典型的确定性数据处理，工作流最优。
2. **约束反向选择架构。** 题目第 5 条硬性要求「**不要自行猜测**」。Agent 的核心能力恰是"自主决策"，自主性越强越容易猜；工作流把每一步钉死，**天然满足不猜测**。约束不是限制，是选型依据。
3. **多 Agent 是过度设计。** 单文档、单一职责链（解析→校验→写表→汇报），没有需要并行探索的分支；引入多 Agent 只增加协调成本与不可控性。

**答辩一句话：**
> 「本题是强规则、强约束、要求『不猜测』的数据处理任务，因此选**确定性工作流**而非 Agent——工作流每一步可复现、可解释、可测试，天然满足不猜测；LLM 只作为**可选的语义交叉校验旁路**，与规则不一致时**升级人工**而非择一，保证无密钥也能完整跑通。」

**术语口径澄清（与 PRD 对齐）：** PRD §3.3 表述为「单体 Agent + 规则引擎 + 人工确认闸门」，其内涵与本 ADR 的「**单体确定性工作流 + 可选 LLM**」一致——PRD 的「单体 Agent」指**单进程、单条职责链的编排单元**，非「具备自主决策的 LLM Agent」。为避免面试与文档口径不一，全项目统一采用本文措辞：**确定性工作流（单体编排）**，并保留一句"若需对外沟通可称单 Agent 形态"的等价说明（见 ADR-002）。

### 5.4 LLM 可选增强的接入点设计

| 接入点 | 位置 | 触发条件 | LLM 作用 | 不一致处置 |
|---|---|---|---|---|
| AP-1 低置信行兜底 | 解析层 `base.py` | 某明细行规则未命中（`UNPARSED_LINE`） | 尝试提取字段**并标注为「LLM 建议」** | 仅作**建议**展示，仍需人工确认；不自动采用 |
| AP-2 语义交叉校验 | 校验层 `cross_check.py` | 规则校验通过时（可选开启） | 独立复核「声明 vs 明细」语义是否一致 | 与规则不一致 → 生成 `LLM_RULE_CONFLICT`（P0）→ 升级人工 |

**一致性处置原则（硬约束）：** 规则结果与 LLM 结果不一致时，**既不取规则也不取 LLM，而是升级为人工确认**（写入 `LLM_RULE_CONFLICT` P0）。避免"二选一"掩盖真实分歧。

**无密钥不降级：** `llm_adapter.py` 在初始化时探测环境变量（如 `LLM_API_KEY`）。缺失时导出 `available=False` 的 no-op 实现；管线检测 `available` 为假即**跳过** AP-1/AP-2 分支，主流程与全部 P0 校验**不受影响**。回归测试集强制 `available=False`，保证核心能力与 LLM 解耦。

### 5.5 演示态 vs 生产态边界

| 能力 | 演示态（本交付） | 生产化缺口（说明即可） |
|---|---|---|

## 6. 端到端验证思路（供 QA 执行）

> 遵循 `spec-as-contract` 的收尾要求：**可执行、覆盖核心成功流 + 关键错误流**。以下步骤是完成定义的一部分，验证通过 + 回归为零才算交付。

### 6.1 环境与启动

```
# 版本锚定（按实际安装版本核对，见 §9 版本锚定）
python -V            # 期望 3.11.x / 3.12.x
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
# 打开 http://127.0.0.1:8000  （轻前端单页操作台）
```

### 6.2 成功流（Happy Path）

| 步 | 操作 | 断言 |
|---|---|---|
| S1 | 粘贴**抖加申请**文本 → 解析 | `line_items` 长度 = 4；条目金额 = [300,200,100,100]；`split_count`=[3,2,1,1]；`summary.declared_total_amount`=700；`anomalies` 中 **P0 数 = 0** |
| S2 | 粘贴**垫付申请**文本 → 解析 | `line_items` 长度 = 5；金额求和 = 2250；**P0 至少含 `COUNT_MISMATCH` 与 `DATE_ORDER_INVALID`** |
| S3 | 对垫付批次逐条裁决 P0（人工确认） | 裁决后该条 `state` 从 `NEEDS_REVIEW` → `RESOLVED` → `READY` |
| S4 | 提交写表（`POST /requests/{id}/commit`） | 返回 `written` 数正确；账号表测试副本对应行「抖加/抖加支付人」被回填；「报价」列**未被改动**；备注写入审计信息 |
| S5 | 查询当日汇总（`GET /summary?date=2026-09-02`） | 抖加当日合计 = 700；垫付当日合计 = 2250 |
| S6 | 生成并获取汇报（`POST /reports/daily` → `GET`） | 汇报含：当日抖加合计、垫付合计、异常清单摘要、待人工确认项计数 |

### 6.3 关键错误流（Error Paths）

| 步 | 操作 | 断言 |
|---|---|---|
| E1 | 对**含未裁决 P0** 的请求直接 `commit` | 返回 **HTTP 409**，`code != 0`，且**未发生任何写表**（测试副本行数与内容不变） |
| E2 | **重复提交**同一垫付文本后 `commit` | 第二次因 `dedup_key` 命中返回 `SKIPPED_ALREADY_WRITTEN`，账号表**不产生重复行** |
| E3 | 提交含**同名两行**博主（葵花夫妇）的匹配 | 产出 `MATCH_AMBIGUOUS`（P0）；未裁决前 `commit` 返回 409 |
| E4 | 提交**无匹配**博主 | 产出 `MATCH_NOT_FOUND`（P0）；断言系统**未自动新建行** |
| E5 | 传入预计打款日早于申请日的文本 | 产出 `DATE_ORDER_INVALID`（P0） |
| E6 | 明细求和与声明总额不符 | 产出 `TOTAL_MISMATCH`（P0） |
| E7 | 关闭 LLM（无密钥）重跑 S1-S2 | 全部核心断言**仍通过**（功能不降级） |
| E8 | 开启 LLM 且注入与规则冲突的模拟返回 | 产出 `LLM_RULE_CONFLICT`（P0），**不采用任一结果**，升级人工 |
| E9 | 抖加批次跨源：文本 700 vs 表内「抖加」列求和 400 | 产出 `CROSS_SOURCE_TOTAL_MISMATCH`（**P1 且不阻断**）；断言该批次仍 **P0 = 0** 且**可正常 commit**；同时**禁止**自动把 400 改写成 700（或反向）——防"跨源不一致被静默调和"与"级别被误升为 P0 导致正常批次无法落表" |

### 6.4 变异定向（防沉默逻辑错误）

对以下**高发静默错误点**写变异用例，注入错误必须让测试变红：

1. 金额归一化：把 `¥1,000` 误算为 `1` 或 `1000.0`（float 精度）。
2. 日期归一化：两位数年份补全错误（`26` → `1926`）。
3. 日期比较：`>=` 写成 `>`，导致相等日误判异常。
4. 幂等键：大小写/全半角未归一，导致重复未被识别。
5. 汇总：抖加与垫付合计串号（把垫付算进抖加）。
6. 字段映射：抖加金额误写入「报价」列。
7. 异常定档：把 `CROSS_SOURCE_TOTAL_MISMATCH` 误实现为**阻断**（P0），导致正常抖加批次无法 commit —— 测试必须变红（守住"阻断阈值不等于噪声"）。
8. 跨源冲突适用条件：把"**不同博主**同字段取值差异"（如文本爆火音乐 vs 表内高高=李老师）误判为 `CROSS_SOURCE_FIELD_CONFLICT`（P0）—— 测试必须变红，正确归属为 `CROSS_SOURCE_SCOPE_MISMATCH`（P1）。

## 9. 已知坑内嵌（本项目硬约束）

1. **抖加 ≠ 报价**：语义与列位都不同，写错即为静默逻辑错误（最致命类）。
2. **「共 7 笔」是声明不是事实**：垫付文本声明 7 笔、明细 5 行，必须以交叉校验暴露，不得"以声明为准"或"以明细为准"擅自抹平。
3. **葵花夫妇在表中两行**：文本单条 VS 表内双行 → 必须 `MATCH_AMBIGUOUS`，禁止选第一行。
4. **空行 / 空抖音号 / 日期格式混杂**：表侧脏数据要在读取阶段归一化并记 P1/P2，不得因解析异常中断整批。
5. **金额用 Decimal 不用 float**：货币求和禁 float。
6. **`26/08/31` 两位数年份**：补全规则必须确定且可审计。
7. **写表前必复制测试副本**：任何写操作只作用于副本，绝不触碰源表。
